# 3. Установка

Два способа: скриптом (служба systemd) или через Docker. Выберите один.

**Требования:** Linux, Python 3.10–3.14, около 200 МБ на само приложение плюс место под копии
писем (примерно равно объёму ящиков). Доступ в интернет нужен только на время установки —
для загрузки библиотек; на сервер без интернета ставят из автономного архива (см. «Установка и
обновление без интернета»).

## Способ А. Скрипт установки (systemd)

Подходит для Debian/Ubuntu, RHEL/Rocky/Alma/Fedora, openSUSE, Arch. Скрипт сам определит дистрибутив.

```bash
cd mail_backup
sudo bash scripts/install.sh
```

Что делает скрипт:
- ставит системные зависимости (`python3`, `python3-venv`, `python3-pip`, `ca-certificates`) и, если получится, `pst-utils`/`libpst` — запасной способ импорта `.pst` (основной встроен в службу и ничего не требует);
- создаёт системного пользователя и группу `mailarchiver`;
- копирует код в `/opt/mailarchiver/app`, создаёт venv и ставит библиотеки **строго по
  `requirements.txt`**, а сам пакет — с `--no-deps` (см. врезку ниже);
- проверяет, что приложение импортируется со всеми зависимостями;
- пишет конфигурацию `/etc/mailarchiver/config.yaml` и каталог данных `/var/lib/mailarchiver`;
- устанавливает и запускает службу systemd, включает автозапуск;
- создаёт команду `mailarchiver` в `/usr/local/bin` (запущенная через `sudo`, она сама выполняется
  от имени службы и с её конфигурацией — так в каталоге данных не появляются файлы root);
- предлагает создать администратора.

> **Почему зависимости ставятся именно так.** В `requirements.txt` у каждой библиотеки заданы
> проверенные границы версий. Если ставить пакет обычной командой `pip install .`, pip заново
> подбирает версии по более свободным границам из `pyproject.toml` и может принести
> непроверенные — однажды это уже приводило к тому, что веб-интерфейс переставал открываться
> после переустановки. Поэтому порядок такой: сначала `pip install -r requirements.txt`, затем
> `pip install --no-deps .`. Если ставите вручную — делайте так же.

При ошибке на любом шаге установка **откатывается** (для чистой установки), данные и конфигурация
не трогаются. Каталог данных проверяется раньше всего остального: если на его месте ссылка на
неподключённый диск, установка откажется, ничего не изменив (см. «Каталог данных на отдельном
диске»).

Каталоги, пользователя и адрес интерфейса можно задать переменными окружения. Пишутся они
**после** `sudo`: написанные перед ним до скрипта не доходят — `sudo` очищает окружение.

```bash
sudo MA_PORT=8080 MA_DATA_DIR=/srv/mailarchiver bash scripts/install.sh
```

| Переменная окружения | Что задаёт (по умолчанию) |
|---|---|
| `MA_INSTALL_DIR=КАТАЛОГ` | каталог установки (`/opt/mailarchiver`) |
| `MA_CONFIG_DIR=КАТАЛОГ` | каталог конфигурации (`/etc/mailarchiver`) |
| `MA_DATA_DIR=КАТАЛОГ` | каталог данных (`/var/lib/mailarchiver`) |
| `MA_USER`, `MA_GROUP` | пользователь и группа службы (`mailarchiver`) |
| `MA_HOST`, `MA_PORT` | адрес и порт веб-интерфейса в новой конфигурации (`127.0.0.1`, `8493`); существующий `config.yaml` не меняется |
| `MA_UNIT_FILE`, `MA_CLI_WRAPPER` | пути unit-файла службы (`/etc/systemd/system/mailarchiver.service`) и команды `mailarchiver` (`/usr/local/bin/mailarchiver`) |

При установке поверх существующей каталоги и пользователя, не заданные переменными, скрипт берёт
из её unit-файла — повторять `MA_*` прежней установки не нужно.

Ещё восемь переменных — `MA_START_TIMEOUT`, `MA_START_TIMEOUT_MAX`, `MA_HEALTH_URL`, `MA_WHEELS`,
`MA_INDEX_URL`, `MA_RELAX_SANDBOX`, `MA_SKIP_OWNER_SCAN` и `MA_PROGRESS_EVERY` — у установки те же,
что у обновления (таблица в разделе «Обновление»); обход каталога данных установка делает, только
когда ставится поверх прежней. Полный
список печатает `bash scripts/install.sh --help`. Параметров у `install.sh` нет: незнакомый
параметр — отказ, а не установка.

Создать администратора вручную (если не создан при установке):
```bash
sudo mailarchiver create-admin
```
Проверить конфигурацию после правки `config.yaml`:
```bash
sudo mailarchiver check-config   # опечатка в имени параметра — предупреждение, неверное значение — ошибка
```

> **Первичная настройка по IP.** Мастер создания первого администратора (при первом открытии
> интерфейса) работает, только если интерфейс открыт по IP-адресу, `localhost`, короткому имени
> без точки или по имени из `server.public_url`. Это защита от атаки DNS rebinding: иначе чужой сайт
> мог бы «переключить» своё доменное имя на адрес вашего сервера и создать администратора раньше
> вас. Обычно достаточно открыть `http://127.0.0.1:8493` через SSH-туннель (см. ниже).

> **Каталоги в /home и /root служба не видит.** Служба запускается с защитой systemd
> (`ProtectHome=true`, `ProtectSystem=full`): файлы в домашних каталогах ей недоступны, писать она
> может только в каталог данных. Общий `/tmp` ей тоже не виден — у неё свой (`PrivateTmp=true`).
> Файл со списком сотрудников, лицензию Aspose и ключ шифрования кладите, например, в
> `/etc/mailarchiver/` или в каталог данных; файлы `.pst` для импорта с сервера — в каталог импорта
> ([10-mailboxes.md](10-mailboxes.md), раздел «Импорт из .pst»).

Управление службой:
```bash
systemctl status mailarchiver
journalctl -u mailarchiver -f
systemctl restart mailarchiver
```

Веб-интерфейс: `http://127.0.0.1:8493` (по умолчанию слушает только локально — см. «Доступ снаружи»).

## Способ Б. Docker Compose

```bash
cd docker
docker compose up -d
```
Данные хранятся в томе `mailarchiver-data` и переживают перезапуск/обновление. Импорт `.pst` внешних
программ не требует; `readpst` включён в образ как запасной способ разбора файла.

Порт публикуется как `127.0.0.1:8493:8493` — только на самой машине. Это сделано намеренно: у
сервиса нет TLS, а интерфейс даёт полный доступ ко всем архивам почты и к паролям ящиков. Наружу
публикуйте через reverse proxy с HTTPS (см. ниже).

**Администратор.** Пароль в `docker-compose.yml` НЕ задан: файл лежит в репозитории, и любой пароль
в нём мгновенно становится общеизвестным. Заведите администратора одним из способов:

```bash
# 1) при первом открытии интерфейса — мастер первичной настройки
# 2) командой (пароль спросят интерактивно, он не попадёт в историю команд и в `ps`):
docker compose exec -it mailarchiver mailarchiver create-admin -u admin
# 3) файлом-секретом: раскомментируйте MA_ADMIN_USER и MA_ADMIN_PASSWORD_FILE
#    вместе с блоком secrets в docker-compose.yml
#    Файл монтируется в контейнер как есть: читать его должен пользователь контейнера (uid 10001)
echo -n 'ВашНадёжныйПароль' > ./admin_password.txt
sudo chown 10001 ./admin_password.txt && chmod 400 ./admin_password.txt
```

Каталог для выгрузок, если монтируете его с хоста (`./exports:/data/exports`), создайте заранее и
отдайте пользователю контейнера: `mkdir -p exports && sudo chown 10001:10001 exports`.

Каталог импорта — для файлов `.pst` и `.ost`, которые импортируются прямо с сервера
([10-mailboxes.md](10-mailboxes.md), раздел «Импорт из .pst»), — в контейнере находится в
`/data/import`. Чтобы класть в него файлы с хоста, смонтируйте каталог хоста так же, как каталог
выгрузок: строка `- ./import:/data/import` в `volumes`, каталог создан заранее и отдан пользователю
контейнера (`mkdir -p import && sudo chown 10001:10001 import`). Каждый положенный файл тоже
отдайте ему: `sudo chown 10001 import/Архив.pst`.

## Каталог данных на отдельном диске

Письма занимают много места, и каталог данных часто держат на другом диске. Способов два: назвать
каталог при установке (`sudo MA_DATA_DIR=/mnt/disk/mailarchiver bash scripts/install.sh`) или
сделать `/var/lib/mailarchiver` символической ссылкой на каталог другого диска. В обоих случаях
диск должен быть подключён **раньше**, чем запускается служба.

Что происходит, когда он не подключён. Каталог данных записан в unit-файле службы
(`ReadWritePaths`), и без него systemd службу не запускает вовсе: `status=226/NAMESPACE`, в журнале
— «Failed to set up mount namespacing: … No such file or directory». До самой программы дело не
доходит, поэтому в её журнале пусто. Не запустится ни новая версия, ни прежняя.

Unit-файл службы о дисках ничего не знает: зависимости от точки монтирования (`RequiresMountsFor`)
в нём нет, systemd ради службы диск не подключает и не ждёт его. Локальный диск из `/etc/fstab`
обычно подключается при загрузке раньше служб. Если ваш подключается позже или может не
подключиться (сетевой, с параметрами `nofail` или `noauto`), добавьте зависимость сами — в
дополнении, которое переживает обновления:

```bash
sudo systemctl edit mailarchiver
```

В открывшийся файл впишите:

```ini
[Unit]
RequiresMountsFor=/mnt/disk/mailarchiver
```

Путь здесь — настоящий каталог на диске (то, куда ведёт ссылка), а не сама ссылка. Тогда systemd
подключит диск перед запуском службы, а если не сможет — не станет её запускать.

**Пул ZFS.** Наборы данных ZFS в `/etc/fstab` не записывают: пул при загрузке импортирует служба
`zfs-import-cache` (по файлу `/etc/zfs/zpool.cache`), а подключает `zfs-mount`. Если пул не записан в
этот файл, после перезагрузки он не импортируется, его точки монтирования (например `/storage`)
остаются пустыми каталогами — и служба не запускается. `RequiresMountsFor` здесь не поможет: unit
монтирования для ZFS заранее нет. Сделайте так:

```bash
sudo zpool set cachefile=/etc/zfs/zpool.cache storage        # имя пула — ваше
sudo systemctl enable zfs-import-cache.service zfs-mount.service zfs.target
sudo systemctl edit mailarchiver
```

и впишите в дополнение:

```ini
[Unit]
Requires=zfs-mount.service
After=zfs-mount.service
```

`update.sh` и `update.sh --check` проверяют каталог данных до остановки службы, `install.sh` — до
любых изменений (ссылку в никуда и неподключённую точку монтирования; каталог, которого ещё нет,
установка создаёт сама). Причина называется прямо:

| Сообщение | Что это значит |
|---|---|
| «Каталог данных … — ссылка на …, а такого каталога сейчас нет» | ссылка ведёт на каталог, которого нет: диск не подключён, пул ZFS не импортирован, каталог перенесли, а ссылку не поправили, или в ссылке опечатка. Скрипт называет неимпортированные пулы ZFS (с командой `zpool import`) и диски, которые сейчас не подключены (по `lsblk`), с командой подключения; ищет базу `mailarchiver.db` рядом с целью ссылки и в обычных местах для данных (`/srv`, `/mnt`, `/media`, `/data`, `/storage`…) и, если нашёл, называет каталоги и готовую команду `ln -sfn …` |
| «Каталог данных … лежит на неподключённом диске — файловая система … из /etc/fstab не подключена» | каталог (или место, куда ведёт ссылка) находится под точкой монтирования из `/etc/fstab`, а она не подключена. Сам каталог при этом может существовать и выглядеть пустым |
| «Нет каталога данных …» | каталога нет вовсе; в сообщении сказано, откуда скрипт взял путь |
| «Служба (пользователь …) не может войти в каталог данных …», «…не может писать в каталог данных …» | дело в правах: названы закрытый каталог и команда, которая его откроет |
| «В каталоге данных нет базы …» (только `update.sh`) | каталог есть и доступен, но базы в нём нет: скорее всего, это не тот каталог. Если базы и не должно быть — `--force` |
| ⚠ «Каталог данных … лежит под точкой монтирования … из /etc/fstab, а она сейчас не подключена» | в каталоге есть данные, и служба с ними работает, но по `/etc/fstab` на этом месте должен быть другой диск. Выясните, какая из двух копий данных настоящая |

Сама программа (служба и команды `mailarchiver`) на ссылке в никуда отвечает так же прямо:
«ОШИБКА: Каталог данных … — ссылка на …, а такого каталога сейчас нет».

Как вернуть службу:

```bash
ls -ld /var/lib/mailarchiver              # ссылка? куда она ведёт
findmnt; lsblk; grep -v '^#' /etc/fstab   # что подключено и что должно быть подключено
sudo mount -a                             # или: sudo mount /точка/монтирования
ls /var/lib/mailarchiver/                 # данные на месте: mailarchiver.db, mailboxes/ …
sudo systemctl reset-failed mailarchiver; sudo systemctl start mailarchiver
```

Если данные **перенесли**, а ссылку сделали с опечаткой (например `/storage/storage/mailarchiver`
вместо `/storage/mailarchiver`) или не поправили, служба после переноса может неделями работать
дальше — с каталогом, открытым до переноса, — и перестать запускаться только при первом
перезапуске, то есть при обновлении. Найдите настоящий каталог (рядом лежат `mailarchiver.db`,
`secret.key` и `mailboxes/`) и направьте на него ссылку — данные при этом не перемещаются:

```bash
sudo find / \( -path /proc -o -path /sys -o -path /run -o -path /dev \) -prune -o -name mailarchiver.db -print
sudo ln -sfn /storage/mailarchiver /var/lib/mailarchiver     # путь — тот, что нашёлся
sudo systemctl reset-failed mailarchiver; sudo systemctl restart mailarchiver
```

Пока диск не подключён, **не создавайте каталог и не меняйте его владельца**: служба запустилась бы
на пустом каталоге и завела новую базу на месте точки монтирования. Диск, который подключается не
через `/etc/fstab`, скрипты распознать не могут: пустую точку монтирования они примут за каталог
без базы или за каталог с неверным владельцем — сначала убедитесь, что диск подключён.

## Установка и обновление без интернета

Библиотеки Python скрипты загружают из сети (PyPI). Для сервера без доступа в интернет собирают
**автономный архив**: кроме исходников, в нём лежит каталог `wheels` с готовыми пакетами (`.whl`)
всех библиотек и самого приложения.

**1. На машине с интернетом** соберите архив:

```bash
cd mail_backup
bash scripts/make_offline_bundle.sh            # архив появится в каталоге проекта
bash scripts/make_offline_bundle.sh /tmp/out   # или в указанном каталоге
```

Нужен `python3` версии 3.10 или новее с pip. Права root не нужны. В каталоге проекта скрипт ничего не
меняет, кроме самого архива, если он кладётся туда (без параметра). Получится файл `mailarchiver-<версия>-offline-<python>-<платформа>.tar.gz`, например
`mailarchiver-1.10.0-offline-cp312-linux_x86_64.tar.gz`.

Пакеты из архива годятся не всякому серверу. У машины сборки и сервера должны совпадать:

- **версия Python** — первые два числа (3.12 и 3.12). Узнать на сервере: `python3 -V` перед первой
  установкой, `/opt/mailarchiver/venv/bin/python -V` перед обновлением;
- **архитектура процессора** — `uname -m` (`x86_64`, `aarch64`).

И система на машине сборки должна быть **не новее**, чем на сервере: пакет, собранный под новую
версию glibc (`ldd --version`), на старую систему не встанет. Проще всего собирать в контейнере или
виртуальной машине с тем же дистрибутивом, что на сервере.

| Параметр `make_offline_bundle.sh` | Что делает |
|---|---|
| `--python ПУТЬ` | интерпретатор, под который собирать (по умолчанию `python3`; то же задаёт переменная `MA_PYTHON`) |
| `--only-binary` | брать только готовые пакеты: если для библиотеки под этот Python готового пакета нет — отказ, а не сборка из исходников. Готовые пакеты меньше привязаны к системе машины сборки, чем собранные на ней |
| `--wheels-dir КАТАЛОГ` | сложить пакеты в этот каталог и оставить его (по умолчанию — временный каталог). Каталог должен быть пустым |
| `-h`, `--help` | справка |

**2. На сервере** — те же команды, что и с обычным архивом:

```bash
tar -xzf mailarchiver-1.10.0-offline-cp312-linux_x86_64.tar.gz
cd mail_backup
sudo bash scripts/update.sh --check   # pip пробной установкой проверит, что пакетов хватает
sudo bash scripts/update.sh           # первая установка: sudo bash scripts/install.sh
```

Найдя каталог `wheels` рядом с исходниками, скрипты ставят всё из него и в сеть не ходят. Пакеты,
лежащие в другом месте, задаются переменной: `sudo MA_WHEELS=/путь/к/wheels bash scripts/update.sh`.
Что при этом идёт иначе:

- pip в окружении не обновляется; приложение ставится из своего пакета — той версии, что записана
  в файле `VERSION` исходников;
- каталог `wheels` в `/opt/mailarchiver/app` не копируется;
- проверка перед обновлением делает пробную установку (`pip install --dry-run`, нужен pip 22.2 или
  новее): если в каталоге нет пакета под Python сервера, обновление откажется до остановки службы.
  Со старым pip остаётся оценка по именам файлов — предупреждение; точно выяснится при установке;
- `install.sh` не вызывает менеджер пакетов дистрибутива, если на сервере уже есть `python3` с
  модулями `venv` и `ensurepip` (проверить: `python3 -c 'import venv, ensurepip'`; в Debian и Ubuntu
  их даёт пакет `python3-venv`). Необязательные `pst-utils`, `rsync` и `ssh` тогда поставьте сами,
  если они нужны. Если модулей нет, скрипт попробует поставить их из репозитория дистрибутива — без
  доступа к нему установка остановится;
- `update.sh` не доустанавливает `rsync` и `ssh`.

Неверный `MA_WHEELS` и каталог без пакета приложения нужной версии — отказ до любых изменений. Если
ставить нужно из сети, а рядом с исходниками лежит каталог `wheels`, уберите или переименуйте его.

**Свой индекс пакетов.** Если в сети есть зеркало PyPI, автономный архив не нужен — назовите
зеркало: `sudo MA_INDEX_URL=https://зеркало/simple/ bash scripts/update.sh` (так же для
`install.sh`). pip получит адрес как `PIP_INDEX_URL`. Проверка перед обновлением опрашивает индекс
и предупреждает, если он не отвечает.

Свой каталог пакетов превращает в такой же архив `python scripts/make_release.py --wheels КАТАЛОГ`:
в каталоге должны лежать готовые пакеты всех библиотек и пакет самого приложения этой версии.

## Контейнеры LXC и OpenVZ: ослабленная защита службы

Служба запускается с защитой systemd: отдельные пространства имён, закрытые `/home` и `/tmp`,
запись только в каталог данных. В непривилегированных контейнерах LXC и OpenVZ без вложенности
(nesting) systemd создать пространство имён не может, и служба не запускается:
`status=226/NAMESPACE`, в журнале — «Failed to set up mount namespacing: Permission denied».
Скрипт установки или обновления в этом случае откатывается и называет два выхода:

1. **Включить вложенность** у контейнера (Proxmox: `pct set <ID> --features nesting=1`) и
   повторить установку или обновление как обычно. Защита службы остаётся полной.
2. **Ослабить защиту** — повторить с переменной `MA_RELAX_SANDBOX=1`:

   ```bash
   sudo MA_RELAX_SANDBOX=1 bash scripts/update.sh    # или scripts/install.sh
   ```

Во втором случае скрипт создаёт дополнение к unit-файлу
`/etc/systemd/system/mailarchiver.service.d/50-relax-sandbox.conf`. Оно отключает настройки,
которым нужны пространства имён или правила доступа к устройствам: `ProtectSystem`, `ProtectHome`,
`PrivateTmp`, `PrivateDevices`, `ProtectProc`, `ProtectKernelTunables`, `ProtectKernelModules`,
`ProtectKernelLogs`, `ProtectControlGroups`, `ProtectClock`, `ProtectHostname`, `ReadWritePaths`,
`RestrictNamespaces`.

Что остаётся: служба по-прежнему работает от непривилегированного пользователя `mailarchiver`, не
может получить новые привилегии (`NoNewPrivileges`), её файлы создаются с `UMask=0077`. Что
теряется: служба видит `/home`, `/root` и общий `/tmp`, и от записи вне каталога данных её
удерживают только обычные права на файлы.

Ослаблять защиту или нет, решает администратор, поэтому сами скрипты этого не делают — даже когда
видят, что сервер — контейнер:

- сам unit-файл не меняется, а дополнение при обновлениях не перезаписывается и не удаляется:
  повторять переменную не нужно. Каждое обновление напоминает: «Служба работает с ослабленной
  защитой»;
- дополнение, созданное запуском, который закончился откатом, убирается;
- если по пути дополнения уже что-то лежит (ваш файл, пустой файл или ссылка на `/dev/null` — так
  дополнение отключают), скрипт его не трогает;
- `MA_RELAX_SANDBOX=0` (или пустое значение) — то же, что без переменной; любое другое значение, кроме
  `1`, — предупреждение «значение не понято», защита не меняется;
- если служба и с дополнением завершается с той же ошибкой, скрипт скажет об этом — остаётся
  включить вложенность.

Вернуть полную защиту (например после включения вложенности):

```bash
sudo rm /etc/systemd/system/mailarchiver.service.d/50-relax-sandbox.conf
sudo systemctl daemon-reload
sudo systemctl restart mailarchiver
```

`uninstall.sh` удаляет это дополнение вместе со службой.

## Обновление

```bash
cd mail_backup   # каталог с НОВОЙ версией исходников
sudo bash scripts/update.sh --check   # по желанию: только проверить, ничего не меняя
sudo bash scripts/update.sh
```

Новую версию распаковывайте в отдельный каталог (например в `/root`), а не внутрь
`/opt/mailarchiver`: из каталога внутри установки скрипт обновлять откажется.

### Проверка перед обновлением

Обновление начинается с проверки — пока служба работает и на диске ничего не тронуто. Её же
запускает отдельно параметр `--check`: служба не останавливается, на диске ничего не меняется, код
возврата 0 означает «обновлять можно». Права root нужны и проверке; запускайте её с теми же
переменными `MA_*`, с которыми будете обновлять.

На каждую проверку — строка со знаком: ✓ — в порядке, ⚠ — предупреждение (обновлению не мешает),
✗ — отказ.

| Что проверяется | Если не в порядке |
|---|---|
| Запуск от root, новые исходники целы, установка на месте, Python и pip её окружения запускаются | отказ сразу. Python или pip окружения не запускаются после обновления Python в системе — пересоздайте окружение установкой поверх: `sudo bash scripts/install.sh` |
| Версии: установленная и новая | та же или более старая — предупреждение (обычно распакован не тот архив) |
| Где лежат новые исходники | внутри каталога установки (или установка внутри них) — отказ. Скрипт запущен прямо из каталога установки — предупреждение: пакет лишь установится заново (без `rsync` — отказ) |
| Пользователь службы существует, может войти в каталоги над установкой и прочитать конфигурацию | отказ: названы закрытый каталог и команда, которая его откроет |
| Каталог данных: он есть, это каталог, служба может в него войти и писать, диск под ним подключён | отказ — см. «Каталог данных на отдельном диске» |
| В каталоге данных есть база | отказ: служба ещё ни разу не запускалась или это не тот каталог. Обходится `--force`. Если установленная версия старая и путь к базе узнать не удалось — предупреждение: обновление пройдёт без копии базы |
| Служба не падает уже сейчас | предупреждение и последние строки её журнала: если причина не в самой программе (нет каталога, занят порт), новая версия тоже не запустится |
| Откуда возьмутся пакеты: каталог `wheels` (обновление без интернета) или индекс пакетов в сети | без сети — отказ, если pip пробной установкой не находит в каталоге нужных пакетов; из сети — предупреждение, если индекс не отвечает |
| Место под копию текущей установки и под копию базы | не хватает для копии установки — отказ; для копии базы — предупреждение: обновление пройдёт без неё |
| Python окружения подходит новой версии (`requires-python`) | отказ. Обходится `--force` |
| Все модули новой версии компилируются этим Python (в памяти, файлы не пишутся) | отказ. Обходится `--force` |
| Новая версия принимает действующую конфигурацию — её `check-config`, прямо из исходников | отказ с текстом ошибки (обходится `--force`); её предупреждения показаны как замечания. Проверить не удалось (новой версии нужна библиотека, которой ещё нет) — предупреждение. Нет самого файла конфигурации — отказ |
| Служба отвечает по адресу проверки (`/health`), по которому её будут ждать после обновления | предупреждение: задайте верный адрес в `MA_HEALTH_URL` |

В конце — итог: «Проверка пройдена — можно обновлять», «Проверка пройдена, предупреждений — N»
или «Проверка не пройдена: ошибок — N, предупреждений — M. Ничего не изменено, служба не
останавливалась» (код возврата 1). После неудачной проверки обычное обновление дальше не идёт:
служба не останавливается, каталог копий не создаётся.

**`--force`** — не считать отказом то, что после установки проверяется ещё раз, уже с откатом:
версию Python, компиляцию модулей, проверку конфигурации новой версией и отсутствие базы. Такой
отказ становится предупреждением с пометкой «--force». Остального `--force` не обходит: за ним
второй проверки нет. Параметр сочетается с `--check`; если проверка прошла только благодаря ему,
обновлять тоже нужно с ним — `sudo bash scripts/update.sh --force`.

### Ход обновления и откат

После проверки, **пока служба ещё работает**, скрипт возвращает службе файлы каталога данных с
чужим владельцем (например, созданные командами, запущенными от root; содержимое `import/` не
трогается). Для этого он обходит весь архив — каждое письмо лежит отдельным файлом, и на сотнях
тысяч писем это минуты, а на диске, который только что подключили, и дольше. Раз в 30 секунд
скрипт пишет, сколько файлов уже проверено, в конце — сколько исправлено. Файлы, которые исправить
не удалось, перечисляются предупреждением — обновление из-за них не останавливается. Пропустить обход
можно переменной `MA_SKIP_OWNER_SCAN=1`.

Затем скрипт останавливает службу, делает резервную копию текущей установки (код,
окружение и unit systemd), обновляет код и зависимости и **до запуска** ещё раз проверяет то, из-за
чего служба чаще всего не поднимается: что она может войти в свой рабочий каталог, прочитать
конфигурацию и писать в каталог данных, что все модули подходят установленной версии Python и что
веб-приложение импортируется. Затем снимает копию базы данных, запускает службу и ждёт ответа
веб-интерфейса (`/health`) — до 180 секунд: первый запуск новой версии обновляет базу, и на большом
архиве это занимает время. Если срок вышел, а служба ещё занята — её процесс тратит процессорное
время, читает или пишет (при обновлении через несколько версий она, например, строит индексы
большой базы), — скрипт ждёт дальше, всего не дольше часа (`MA_START_TIMEOUT_MAX`), и раз в
30 секунд пишет, сколько прошло и сколько служба прочитала и записала. Откатывает он службу,
которая за 10 секунд не сделала ничего, — зависшую.

При ошибке — **автоматический откат**: возвращаются код, окружение, unit и база данных (если новая
версия успела запуститься), прежняя версия запускается, и скрипт проверяет, что она поднялась.
Причина отказа печатается тут же: последние строки журнала службы и, для частых случаев, что с ней
делать. Письма и конфигурация не трогаются. Откатом заканчивается и прерванное обновление — Ctrl-C,
`kill`, обрыв сессии SSH; на медленном канале всё же надёжнее запускать его в `screen` или `tmux`.

Если служба падала ещё до обновления и после отката тоже не поднялась, скрипт говорит об этом
прямо: причина, скорее всего, прежняя и не в обновлении.

### Параметры и переменные окружения

| Параметр или переменная | Что делает |
|---|---|
| `--check` | Только проверить, пройдёт ли обновление: служба не останавливается, на диске ничего не меняется. |
| `--force` | Понизить до предупреждений те отказы проверки, которые после установки проверяются ещё раз (см. выше). |
| `-h`, `--help` | Справка: параметры и переменные. Права root для неё не нужны. |
| `MA_START_TIMEOUT=600` | Сколько секунд ждать ответа веб-интерфейса (по умолчанию 180). Служба, которая к этому сроку ещё занята, ждётся дольше — см. следующую строку. |
| `MA_START_TIMEOUT_MAX=14400` | Сколько секунд всего ждать службу, которая к сроку `MA_START_TIMEOUT` не ответила, но ещё работает — обновляет базу (по умолчанию 3600). |
| `MA_HEALTH_URL=http://адрес:порт/health` | Свой адрес проверки. По умолчанию он берётся из `server.host` и `server.port`. |
| `MA_SKIP_DB_BACKUP=1` | Не копировать базу перед обновлением. Тогда при откате база останется в том виде, в каком её оставит новая версия. |
| `MA_KEEP_DB_BACKUP=1` | Не удалять копию базы после успешного обновления (она остаётся в `/opt/mailarchiver/backups/db_ДАТА`). |
| `MA_SKIP_OWNER_SCAN=1` | Не обходить весь каталог данных в поисках файлов с чужим владельцем (см. «Ход обновления и откат»). Верхний уровень — база, ключ, каталоги — проверяется всё равно. |
| `MA_PROGRESS_EVERY=60` | Раз в сколько секунд долгие шаги — этот обход и ожидание запуска службы — пишут, как идут дела (по умолчанию 30). |
| `MA_WHEELS=КАТАЛОГ` | Каталог с пакетами `.whl` для обновления без интернета. По умолчанию — каталог `wheels` рядом с исходниками, если он есть (см. «Установка и обновление без интернета»). |
| `MA_INDEX_URL=URL` | Свой индекс пакетов (зеркало PyPI) для обновления из сети. |
| `MA_RELAX_SANDBOX=1` | Ослабить защиту службы — для контейнеров LXC и OpenVZ без вложенности (см. «Контейнеры LXC и OpenVZ»). |
| `MA_DATA_DIR=КАТАЛОГ` | Каталог данных, если скрипт определил его неверно. По умолчанию он берётся из конфигурации установленной версии (`paths.data_dir`), затем из unit-файла. |
| `MA_INSTALL_DIR`, `MA_CONFIG_DIR`, `MA_USER`, `MA_GROUP` | Каталоги установки и конфигурации, пользователь и группа службы. По умолчанию берутся из действующего unit-файла. |
| `MA_UNIT_FILE`, `MA_CLI_WRAPPER` | Пути unit-файла службы и команды `mailarchiver`, если они не стандартные. |

Пример: `sudo MA_START_TIMEOUT=600 bash scripts/update.sh`. Переменные пишутся **после** `sudo`:
написанные перед ним (`MA_START_TIMEOUT=600 sudo bash …`) до скрипта не доходят — `sudo` очищает
окружение. Режим проверки поэтому включается только параметром `--check`, переменной для него нет.
Незнакомый параметр — отказ с кодом 2.

Каталоги и пользователя службы скрипт берёт из действующего unit-файла: если при установке
задавались `MA_INSTALL_DIR`, `MA_USER` и подобные, повторять их при обновлении не нужно.

Права на файлы скрипты выставляют сами (каталоги 755, файлы 644, владелец root) — права распакованного
архива и `umask` у root на установку не влияют. Архив выпуска собирает `python scripts/make_release.py`.

> **Свои настройки службы** (например лимит памяти `MemoryMax`) задавайте не в самом unit-файле —
> он перезаписывается при каждом обновлении, — а в дополнении: `sudo systemctl edit mailarchiver`.

### Что меняется при обновлении на конкретную версию

> **Обновление на 1.3.0.** Проверьте после обновления: общий срок хранения («Хранить дней»)
> теперь действует, только если включена «Общая очистка по сроку», — но тогда уже ко **всем**
> ящикам со сроком «как в общих настройках» (раньше только к ящикам со своим расписанием
> очистки). Расписания «очистка в 03:30», которые прежние версии заводили ящикам сами,
> удаляются: очистку ставит ежедневный обход (`retention.cron`). Параметры
> `backup.per_account_concurrency` и `export.outlook_target` больше ни на что не влияют (с одним
> ящиком одновременно работает одно задание); ящики сотрудникам заводятся, только когда в шаблоне
> указан IMAP-сервер. Подробно — в CHANGELOG.md.

> **Обновление на 1.4.0.** Что начнётся само сразу после обновления:
>
> - **Индексация поиска** (`search.enabled`, включена): новые и все старые письма читаются по
>   одному разу, чтобы по ним работал поиск. На большом архиве первое индексирование занимает
>   часы и нагружает диск; оно идёт порциями по 10 минут с низким приоритетом и уступает очередь
>   копированиям ящиков. Не нужен поиск — выключите «Настройки → Поиск по письмам».
> - **Ежедневный снимок базы** в 06:00 в каталог `snapshots/` каталога данных (хранятся 3
>   последних, сжатые). Отключить — «Хранить снимков базы: 0».
> - **Еженедельная сводка** на почту по понедельникам (только если уведомления включены).
> - **Уволенные сотрудники** (`employees.dismiss_from_file`, включено): при первой же
>   синхронизации сотрудники, которые числятся в справочнике работающими, а в выгрузке помечены
>   «не работает», будут отмечены уволенными — их ящикам поставится последняя копия, затем
>   копирование выключится, а архив будет удерживаться 5 лет. Если таких окажется больше 20 %
>   (защита от испорченной выгрузки), увольнения не применятся, а в итоге синхронизации будет
>   предупреждение. Карточки, бывшие «в архиве» до обновления, не меняются — удержание для их
>   ящиков при необходимости поставьте вручную (меню ящика → «Удержание архива»). Не нужно —
>   выключите «Сотрудники → Отмечать уволенных по выгрузке» **до** ближайшей синхронизации.
>
> Копия архива вне сервера, метрики мониторинга и вход через администратора почты по умолчанию
> выключены. Для копии на другой сервер по SSH нужны `rsync` и `ssh` — `update.sh` доустановит их
> сам, если их нет. Подробно — в CHANGELOG.md.

> **Обновление на 1.5.0.** Проверьте после обновления:
>
> - **Дни недели в расписаниях** теперь считаются как в crontab: 1 — понедельник … 6 — суббота,
>   0 и 7 — воскресенье. Прежние версии сдвигали числа на день: `0 2 * * 1-5` («по будням»)
>   срабатывало со вторника по субботу, `1` — по вторникам. Расписания с числами дней недели
>   начнут срабатывать в те дни, которые в них написаны; **еженедельная сводка** (`0 8 * * 1`)
>   будет приходить по понедельникам, а не по вторникам. Если выражения подгонялись под старое
>   поведение — верните обычную запись. Расписания с `*` (каждый день) не меняются.
> - При первом запуске база **один раз перестраивает таблицу расписаний** (чтобы в ней могли быть
>   расписания без ящика — «копирование всех ящиков по очереди»); расписания сохраняются. Добавляется
>   таблица истории групповых действий.
>

## Удаление

```bash
sudo bash scripts/uninstall.sh                 # удалить сервис, ДАННЫЕ СОХРАНИТЬ
sudo bash scripts/uninstall.sh --purge         # удалить всё, включая данные и конфигурацию
sudo bash scripts/uninstall.sh --remove-user   # удалить и пользователя службы
```

Без `--purge` данные и конфигурация остаются; в терминале скрипт спросит о них и покажет, что
именно будет удалено. С `--purge` удаляется и пользователь службы — если данные и конфигурацию
удалось удалить полностью. Незнакомый параметр — отказ: `uninstall.sh --check` ничего не удалит.

- **Нестандартная установка.** Unit-файл скрипт удаления не читает: если при установке задавались
  `MA_INSTALL_DIR`, `MA_CONFIG_DIR`, `MA_DATA_DIR`, `MA_USER`, `MA_UNIT_FILE` или `MA_CLI_WRAPPER`,
  задайте те же (после `sudo`): `sudo MA_DATA_DIR=/srv/mail bash scripts/uninstall.sh --purge`.
- **Дополнения к unit-файлу.** Вместе со службой удаляется дополнение `50-relax-sandbox.conf` (его
  создаёт `MA_RELAX_SANDBOX=1`). Остальные файлы из `mailarchiver.service.d` — ваши правки через
  `systemctl edit` — остаются, и скрипт о них напоминает.
- **Каталог данных — ссылка на другой диск.** `--purge` удаляет каталог, на который ведёт ссылка,
  и саму ссылку. Если диск не подключён, удаляется только ссылка, а скрипт сообщает: то, что
  лежит на том диске, не удалено, — и завершается с кодом 1; пользователь службы в этом случае
  остаётся (данные на том диске принадлежат ему). Путь, ведущий в корень или в каталог верхнего уровня
  (`MA_DATA_DIR=/`, ссылка на `/srv`), не удаляется вовсе.
- Если удалить удалось не всё, скрипт перечисляет, что осталось и почему, и возвращает код 1.

## Доступ снаружи (reverse proxy + HTTPS)

По умолчанию сервис слушает `127.0.0.1` — это безопасно. Чтобы открыть доступ из сети, поставьте
перед ним nginx/traefik с TLS (см. раздел «Безопасность» в полной документации). Не открывайте порт
`8493` напрямую в интернет по HTTP.

**Обязательно при работе за прокси** — иначе защита от подбора пароля работать не будет:

```yaml
server:
  behind_proxy: true              # доверять заголовкам X-Forwarded-*
  trusted_proxies: "127.0.0.1"    # адрес(а) вашего nginx/traefik; допустимы сети: 10.0.0.0/8
  public_url: "https://mail-backup.example.ru"
security:
  secure_cookie: true             # cookie только по HTTPS
```

Как это работает. Настоящим адресом клиента считается **первый справа** элемент цепочки
`X-Forwarded-For`, которого нет в `trusted_proxies`. Левую часть цепочки дописывает сам клиент, и
если верить ей — тот, кто подбирает пароль, будет приходить «с нового адреса» на каждой попытке, и
ни один счётчик неудач не сработает. Если `trusted_proxies` не заполнен, а `behind_proxy` включён,
сервис откажется стартовать и скажет об этом.

Обратная ошибка так же вредна: `behind_proxy: false` за nginx означает, что у **всех** клиентов
адрес один и тот же (адрес прокси), и полсотни неудачных попыток одного злоумышленника закроют вход
всей организации на время блокировки.

При доступе по доменному имени укажите его в `public_url` — по нему проверяется источник запросов
(в том числе WebSocket живого дашборда).

Минимальный nginx:
```nginx
location / {
    proxy_pass http://127.0.0.1:8493;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_http_version 1.1;                       # для WebSocket (живой дашборд)
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection "upgrade";
}
```

Быстрый доступ без публикации — SSH-туннель:
```bash
ssh -L 8493:127.0.0.1:8493 user@ваш-сервер
# затем откройте http://127.0.0.1:8493 на своём компьютере
```
