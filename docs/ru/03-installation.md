# 3. Установка

Два способа: скриптом (служба systemd) или через Docker. Выберите один.

**Требования:** Linux, Python 3.10–3.14, около 200 МБ на само приложение плюс место под копии
писем (примерно равно объёму ящиков). Доступ в интернет нужен только на время установки —
для загрузки библиотек.

## Способ А. Скрипт установки (systemd)

Подходит для Debian/Ubuntu, RHEL/Rocky/Alma/Fedora, openSUSE, Arch. Скрипт сам определит дистрибутив.

```bash
cd mail_backup
sudo bash scripts/install.sh
```

Что делает скрипт:
- ставит системные зависимости (`python3`, `python3-venv`, `python3-pip`, `ca-certificates`) и, если получится, `pst-utils`/`libpst` — запасной способ импорта `.pst` (основной встроен в службу и ничего не требует);
- создаёт системного пользователя и группу `mailarchiver`;
- копирует код в `/opt/mailarchiver/app`, создаёт venv и ставит библиотеки **строго по
  `requirements.txt`**, а сам пакет — с `--no-deps` (см. врезку ниже);
- проверяет, что приложение импортируется со всеми зависимостями;
- пишет конфигурацию `/etc/mailarchiver/config.yaml` и каталог данных `/var/lib/mailarchiver`;
- устанавливает и запускает службу systemd, включает автозапуск;
- создаёт команду `mailarchiver` в `/usr/local/bin` (запущенная через `sudo`, она сама выполняется
  от имени службы и с её конфигурацией — так в каталоге данных не появляются файлы root);
- предлагает создать администратора.

> **Почему зависимости ставятся именно так.** В `requirements.txt` у каждой библиотеки заданы
> проверенные границы версий. Если ставить пакет обычной командой `pip install .`, pip заново
> подбирает версии по более свободным границам из `pyproject.toml` и может принести
> непроверенные — однажды это уже приводило к тому, что веб-интерфейс переставал открываться
> после переустановки. Поэтому порядок такой: сначала `pip install -r requirements.txt`, затем
> `pip install --no-deps .`. Если ставите вручную — делайте так же.

При ошибке на любом шаге установка **откатывается** (для чистой установки), данные и конфигурация
не трогаются.

Создать администратора вручную (если не создан при установке):
```bash
sudo mailarchiver create-admin
```
Проверить конфигурацию после правки `config.yaml`:
```bash
sudo mailarchiver check-config   # опечатка в имени параметра — предупреждение, неверное значение — ошибка
```

> **Первичная настройка по IP.** Мастер создания первого администратора (при первом открытии
> интерфейса) работает, только если интерфейс открыт по IP-адресу, `localhost`, короткому имени
> без точки или по имени из `server.public_url`. Это защита от атаки DNS rebinding: иначе чужой сайт
> мог бы «переключить» своё доменное имя на адрес вашего сервера и создать администратора раньше
> вас. Обычно достаточно открыть `http://127.0.0.1:8493` через SSH-туннель (см. ниже).

> **Каталоги в /home и /root служба не видит.** Служба запускается с защитой systemd
> (`ProtectHome=true`, `ProtectSystem=full`): файлы в домашних каталогах ей недоступны, писать она
> может только в каталог данных. Файл со списком сотрудников, лицензию Aspose и ключ шифрования
> кладите, например, в `/etc/mailarchiver/` или в каталог данных.

Управление службой:
```bash
systemctl status mailarchiver
journalctl -u mailarchiver -f
systemctl restart mailarchiver
```

Веб-интерфейс: `http://127.0.0.1:8493` (по умолчанию слушает только локально — см. «Доступ снаружи»).

## Способ Б. Docker Compose

```bash
cd docker
docker compose up -d
```
Данные хранятся в томе `mailarchiver-data` и переживают перезапуск/обновление. Импорт `.pst` внешних
программ не требует; `readpst` включён в образ как запасной способ разбора файла.

Порт публикуется как `127.0.0.1:8493:8493` — только на самой машине. Это сделано намеренно: у
сервиса нет TLS, а интерфейс даёт полный доступ ко всем архивам почты и к паролям ящиков. Наружу
публикуйте через reverse proxy с HTTPS (см. ниже).

**Администратор.** Пароль в `docker-compose.yml` НЕ задан: файл лежит в репозитории, и любой пароль
в нём мгновенно становится общеизвестным. Заведите администратора одним из способов:

```bash
# 1) при первом открытии интерфейса — мастер первичной настройки
# 2) командой (пароль спросят интерактивно, он не попадёт в историю команд и в `ps`):
docker compose exec -it mailarchiver mailarchiver create-admin -u admin
# 3) файлом-секретом: раскомментируйте MA_ADMIN_USER и MA_ADMIN_PASSWORD_FILE
#    вместе с блоком secrets в docker-compose.yml
#    Файл монтируется в контейнер как есть: читать его должен пользователь контейнера (uid 10001)
echo -n 'ВашНадёжныйПароль' > ./admin_password.txt
sudo chown 10001 ./admin_password.txt && chmod 400 ./admin_password.txt
```

Каталог для выгрузок, если монтируете его с хоста (`./exports:/data/exports`), создайте заранее и
отдайте пользователю контейнера: `mkdir -p exports && sudo chown 10001:10001 exports`.

## Обновление

```bash
cd mail_backup   # каталог с НОВОЙ версией исходников
sudo bash scripts/update.sh
```
Скрипт делает резервную копию текущей установки (код, окружение и unit systemd), обновляет код и
зависимости и **до запуска** проверяет то, из-за чего служба чаще всего не поднимается: что она может
войти в свой рабочий каталог, прочитать конфигурацию и писать в каталог данных, что все модули
подходят установленной версии Python и что веб-приложение импортируется. Затем снимает копию базы
данных, запускает службу и ждёт ответа веб-интерфейса (`/health`) — до 180 секунд: первый запуск
новой версии обновляет базу, и на большом архиве это занимает время.

При ошибке — **автоматический откат**: возвращаются код, окружение, unit и база данных (если новая
версия успела запуститься), прежняя версия запускается, и скрипт проверяет, что она поднялась.
Причина отказа печатается тут же: последние строки журнала службы и, для частых случаев, что с ней
делать. Письма и конфигурация не трогаются. Откатом заканчивается и прерванное обновление — Ctrl-C,
`kill`, обрыв сессии SSH; на медленном канале всё же надёжнее запускать его в `screen` или `tmux`.

| Переменная окружения | Что делает |
|---|---|
| `MA_START_TIMEOUT=600` | Сколько секунд ждать ответа веб-интерфейса (по умолчанию 180). Увеличьте, если база большая и первый запуск новой версии длится дольше. |
| `MA_HEALTH_URL=http://адрес:порт/health` | Свой адрес проверки. По умолчанию он берётся из `server.host` и `server.port`. |
| `MA_SKIP_DB_BACKUP=1` | Не копировать базу перед обновлением. Тогда при откате база останется в том виде, в каком её оставит новая версия. |
| `MA_KEEP_DB_BACKUP=1` | Не удалять копию базы после успешного обновления (она остаётся в `/opt/mailarchiver/backups/db_ДАТА`). |

Пример: `sudo MA_START_TIMEOUT=600 bash scripts/update.sh`.

Каталоги и пользователя службы скрипт берёт из действующего unit-файла: если при установке
задавались `MA_INSTALL_DIR`, `MA_DATA_DIR`, `MA_USER` и подобные, повторять их при обновлении не нужно.

Права на файлы скрипты выставляют сами (каталоги 755, файлы 644, владелец root) — права распакованного
архива и `umask` у root на установку не влияют. Архив выпуска собирает `python scripts/make_release.py`.

> **Свои настройки службы** (например лимит памяти `MemoryMax`) задавайте не в самом unit-файле —
> он перезаписывается при каждом обновлении, — а в дополнении: `sudo systemctl edit mailarchiver`.

> **Обновление на 1.3.0.** Проверьте после обновления: общий срок хранения («Хранить дней»)
> теперь действует, только если включена «Общая очистка по сроку», — но тогда уже ко **всем**
> ящикам со сроком «как в общих настройках» (раньше только к ящикам со своим расписанием
> очистки). Расписания «очистка в 03:30», которые прежние версии заводили ящикам сами,
> удаляются: очистку ставит ежедневный обход (`retention.cron`). Параметры
> `backup.per_account_concurrency` и `export.outlook_target` больше ни на что не влияют (с одним
> ящиком одновременно работает одно задание); ящики сотрудникам заводятся, только когда в шаблоне
> указан IMAP-сервер. Подробно — в CHANGELOG.md.

> **Обновление на 1.4.0.** Что начнётся само сразу после обновления:
>
> - **Индексация поиска** (`search.enabled`, включена): новые и все старые письма читаются по
>   одному разу, чтобы по ним работал поиск. На большом архиве первое индексирование занимает
>   часы и нагружает диск; оно идёт порциями по 10 минут с низким приоритетом и уступает очередь
>   копированиям ящиков. Не нужен поиск — выключите «Настройки → Поиск по письмам».
> - **Ежедневный снимок базы** в 06:00 в каталог `snapshots/` каталога данных (хранятся 3
>   последних, сжатые). Отключить — «Хранить снимков базы: 0».
> - **Еженедельная сводка** на почту по понедельникам (только если уведомления включены).
> - **Уволенные сотрудники** (`employees.dismiss_from_file`, включено): при первой же
>   синхронизации сотрудники, которые числятся в справочнике работающими, а в выгрузке помечены
>   «не работает», будут отмечены уволенными — их ящикам поставится последняя копия, затем
>   копирование выключится, а архив будет удерживаться 5 лет. Если таких окажется больше 20 %
>   (защита от испорченной выгрузки), увольнения не применятся, а в итоге синхронизации будет
>   предупреждение. Карточки, бывшие «в архиве» до обновления, не меняются — удержание для их
>   ящиков при необходимости поставьте вручную (меню ящика → «Удержание архива»). Не нужно —
>   выключите «Сотрудники → Отмечать уволенных по выгрузке» **до** ближайшей синхронизации.

> выключены. Для копии на другой сервер по SSH нужны `rsync` и `ssh` — `update.sh` доустановит их
> сам, если их нет. Подробно — в CHANGELOG.md.

> **Обновление на 1.5.0.** Проверьте после обновления:
>
> - **Дни недели в расписаниях** теперь считаются как в crontab: 1 — понедельник … 6 — суббота,
>   0 и 7 — воскресенье. Прежние версии сдвигали числа на день: `0 2 * * 1-5` («по будням»)
>   срабатывало со вторника по субботу, `1` — по вторникам. Расписания с числами дней недели
>   начнут срабатывать в те дни, которые в них написаны; **еженедельная сводка** (`0 8 * * 1`)

>   расписания без ящика — «копирование всех ящиков по очереди»); расписания сохраняются. Добавляется
>   таблица истории групповых действий.

> когда вы заведёте его в «Расписаниях» ([18-schedules.md](18-schedules.md)). Подробно — в
> CHANGELOG.md.

>
> - **Ящики со сроком хранения** (например, «3 дня») больше не скачивают письма старше срока — ни
>   при первом копировании, ни после копии «с нуля». В итоге копирования — «Писем старше срока
>   хранения ящика не скачано: N»; номера таких писем запоминаются, и следующие копирования их не
>   перепроверяют. Увеличили срок или поставили архив на удержание — письма, ещё лежащие на

> - **Письмо об итоге прохода «все ящики по очереди»** перечисляет поимённо ящики с ошибкой,

Для Docker: пересоберите образ и поднимите заново — `docker compose up -d --build`.

## Удаление

```bash
sudo bash scripts/uninstall.sh          # удалить сервис, ДАННЫЕ СОХРАНИТЬ
sudo bash scripts/uninstall.sh --purge  # удалить всё, включая данные и конфигурацию
```

## Доступ снаружи (reverse proxy + HTTPS)

По умолчанию сервис слушает `127.0.0.1` — это безопасно. Чтобы открыть доступ из сети, поставьте
перед ним nginx/traefik с TLS (см. раздел «Безопасность» в полной документации). Не открывайте порт
`8493` напрямую в интернет по HTTP.

**Обязательно при работе за прокси** — иначе защита от подбора пароля работать не будет:

```yaml
server:
  behind_proxy: true              # доверять заголовкам X-Forwarded-*
  trusted_proxies: "127.0.0.1"    # адрес(а) вашего nginx/traefik; допустимы сети: 10.0.0.0/8
  public_url: "https://mail-backup.example.ru"
security:
  secure_cookie: true             # cookie только по HTTPS
```

Как это работает. Настоящим адресом клиента считается **первый справа** элемент цепочки
`X-Forwarded-For`, которого нет в `trusted_proxies`. Левую часть цепочки дописывает сам клиент, и
если верить ей — тот, кто подбирает пароль, будет приходить «с нового адреса» на каждой попытке, и
ни один счётчик неудач не сработает. Если `trusted_proxies` не заполнен, а `behind_proxy` включён,
сервис откажется стартовать и скажет об этом.

Обратная ошибка так же вредна: `behind_proxy: false` за nginx означает, что у **всех** клиентов
адрес один и тот же (адрес прокси), и полсотни неудачных попыток одного злоумышленника закроют вход
всей организации на время блокировки.

При доступе по доменному имени укажите его в `public_url` — по нему проверяется источник запросов
(в том числе WebSocket живого дашборда).

Минимальный nginx:
```nginx
location / {
    proxy_pass http://127.0.0.1:8493;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_http_version 1.1;                       # для WebSocket (живой дашборд)
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection "upgrade";
}
```

Быстрый доступ без публикации — SSH-туннель:
```bash
ssh -L 8493:127.0.0.1:8493 user@ваш-сервер
# затем откройте http://127.0.0.1:8493 на своём компьютере
```
