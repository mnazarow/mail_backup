# 2. Методология работы

## Общая архитектура

MailArchiver состоит из взаимодействующих компонентов:

- **Веб-интерфейс (FastAPI)** — управление и мониторинг из браузера, REST API и WebSocket для живых
  обновлений.
- **Очередь заданий** — все тяжёлые операции (бэкап, экспорт, восстановление) выполняются фоновыми
  воркерами; видно прогресс, есть отмена и повторы.
- **Групповые действия** — одно действие сразу для многих ящиков: сначала проверка по каждому ящику,
  потом выполнение, история операций ([17-bulk.md](17-bulk.md)).
- **Планировщик (APScheduler)** — по расписанию ставит задания в очередь.
- **IMAP-движок** — подключение к почтовым серверам, скачивание и заливка писем.
- **Хранилище (Maildir)** — локальные копии писем на диске.
- **База данных (SQLite)** — индекс писем, задания, настройки, история, пользователи, индекс
  полнотекстового поиска (FTS5).
- **Копия вне сервера** — ежедневно отправляет новые файлы писем и снимки базы в сетевую папку, на
  другой сервер (rsync по SSH) или в S3-хранилище.
- **Мониторинг** — метрики `/metrics` для Prometheus/Zabbix и еженедельная сводка на почту.

```
Веб-интерфейс ─▶ Очередь ─▶ IMAP-движок ─▶ Почтовый сервер
                   │  ▲                └─▶ Хранилище Maildir (.eml)
   Планировщик ────┘  └── База (SQLite): индекс, задания, поиск
                                   │
        Копия вне сервера ◀────────┴── файлы писем + снимки базы ─▶ папка / SSH / S3
```

Фоновые задания, которые ставит сам сервис: копирование по расписаниям, ежедневная очистка по
сроку хранения, индексация поиска (каждые 10 минут, если есть новые письма), копия вне сервера и
снимок базы (раз в сутки), синхронизация сотрудников, обслуживание базы. Тяжёлые служебные задания
(индексация, отчёт об одинаковых вложениях) идут порциями и уступают очередь копированиям ящиков.

## Инкрементальный алгоритм бэкапа

Сервис не скачивает всё заново при каждом запуске. Он опирается на механизмы IMAP:

1. У каждого письма в папке есть уникальный номер **UID**.
2. У папки есть признак **UIDVALIDITY**. Если он изменился (переезд почты на другой сервер,
   папку пересоздали), прежние номера писем недействительны — так требует протокол IMAP. Сервис
   не качает такую папку заново целиком: письма, которые уже есть в архиве, он узнаёт по
   Message-ID, размеру и дате (подробнее — ниже).
3. Сервис хранит в БД, какие `(UIDVALIDITY, UID)` уже сохранены, и **докачивает только новые** письма.
4. Если у ящика задан срок хранения, письма старше него **не скачиваются вовсе** (ниже).

Порядок выполнения:

1. Подключение к ящику, получение списка папок, фильтрация по правилам (белый/чёрный списки).
2. **Фаза планирования**: для каждой папки определяются новые письма и общий объём работы (для прогресса).
3. **Фаза загрузки**: письма скачиваются пакетами (UID FETCH), сохраняются в Maildir, заносятся в индекс.
4. Обновление состояния папок и статистики.

Ошибка в одной папке не прерывает весь бэкап — она логируется и учитывается, остальные папки
продолжают копироваться. Обрыв связи посреди копирования не начинает всё заново: сервис
переподключается и продолжает с того же места (подряд — не больше трёх переподключений без
продвижения). Если задание всё же сорвалось (сервер недоступен), оно повторяется с нарастающей
задержкой; отложенный повтор хранится в базе и переживает перезапуск службы.

С одним ящиком одновременно работает **только одно** задание (копирование, очистка, проверка,
перешифровка, экспорт, восстановление) — они не мешают друг другу. При штатной остановке службы
идущие задания возвращаются в очередь и продолжаются после запуска.

### Смена UIDVALIDITY: переезд без повторного скачивания

Раньше смена UIDVALIDITY означала повторное скачивание всей папки, а прежние записи оставались в
архиве «историческими» — переезд почты на другой сервер удваивал архив. С версии 1.6.0 при смене
UIDVALIDITY сервис спрашивает у сервера только заголовки Message-ID и Date и размер писем
(`UID FETCH … (RFC822.SIZE BODY.PEEK[HEADER.FIELDS (MESSAGE-ID DATE)])`, без тел) и сверяет их с
архивом:

- письмо, у которого сочетание «Message-ID, размер, дата (заголовок Date)» встречается **ровно
  один раз** и в архиве, и на сервере, привязывается к новому номеру: запись индекса получает новые
  UIDVALIDITY и UID, файл остаётся тем же, повторно ничего не скачивается (дату письма в архиве
  сервис читает из заголовков его файла);
- письма без Message-ID или заголовка Date, с другим размером или датой (сервер пересобрал письмо,
  ежедневные отчёты с одним Message-ID) и **неоднозначные** (несколько писем с одинаковыми
  Message-ID, размером и датой)
  скачиваются, как раньше: сопоставление «по порядку» могло бы привязать номер сервера к чужому
  письму архива, и новое письмо не скачалось бы никогда;
- записи, которых на новом сервере нет, остаются в архиве — ничего не удаляется.

В журнале задания — сколько писем узнано, сколько осталось скачать; в итоге — «Сервер сменил
нумерацию писем (UIDVALIDITY): узнано в архиве писем — N».

### Письма старше срока хранения не скачиваются

Если у ящика задан срок хранения (например, 3 дня), письма старше него не скачиваются: ночная
очистка всё равно удалила бы их из копии, а при первом копировании (и после копии «с нуля») это
была бы вся многолетняя история ящика. Отбор в два шага:

1. поиск по дате на сервере (`UID SEARCH UID <новые> SINCE <срок + 1 день>`) быстро находит свежие
   письма;
2. письма, которых нет в ответе поиска, проверяются по их собственной дате (`FETCH INTERNALDATE`),
   и не скачиваются только те, что действительно старше срока. Сбойный или неполный ответ поиска
   не лишит копию новых писем; если сервер не выполнил ни одну из команд — скачивается всё.

Номера отсеянных писем запоминаются так же, как номера писем, удалённых очисткой: следующие
прогоны их не перепроверяют. Когда срок хранения увеличивают или архив ставят на удержание
(увольнение, проверка), эта память сбрасывается, и письма, ещё лежащие на сервере, скачиваются.
Ящик на удержании копируется целиком — срок хранения на нём не действует.

## Копирование всех ящиков по очереди

Обычно каждый ящик копируется своим заданием, и одновременно идёт столько копирований, сколько
разрешено («Одновременных заданий»). Задание **«Копирование всех ящиков по очереди»** работает
иначе: одно задание проходит все включённые ящики строго по одному и никогда не копирует два ящика
сразу ([18-schedules.md](18-schedules.md)).

- Порядок — по давности последней попытки (удачная копия, проверка входа, неудачный прогон):
  ящики, до которых прошлый проход не дошёл, идут первыми.
- Ящик, который копирует проход, «занят»: очередь не запускает по нему других заданий, пока проход
  с ним не закончит. Ящик, занятый своим заданием, откладывается в конец прохода.
- Ход прохода (какие ящики готовы, итоги) хранится в базе: перезапуск службы продолжает проход, а
  не начинает заново.
- Сервер, не ответивший на 5 ящиках подряд, в этом проходе пропускается (по каждому серверу
  отдельно), его ящики будут первыми в следующий раз.
- «Не начинать новые ящики после ЧЧ:ММ» отсчитывается от времени запуска по расписанию, а не от
  фактического старта: проход, дождавшийся места в очереди позже, всё равно закончит к утру.

Папка, которую сервер не даёт открыть, не считается пропажей писем сразу: несколько прогонов подряд
она помечается «копия неполная» (`backup.unreadable_folder_grace_runs`), а в деталях задания есть
кнопка «Больше не копировать эти папки». Папка-контейнер (в ней нет писем, только подпапки)
пропускается молча.

## Копирование заново

Обычная копия инкрементальная: письмо, уже записанное в индекс, у сервера повторно не запрашивается.
Когда архив нужно перепроверить целиком, в меню ящика есть **«🔄 Скопировать заново»** с двумя
режимами:

| Режим | Что делает | Что происходит с прежней копией |
|-------|-----------|----------------|
| Докачать потерянные письма | Сверяет индекс с файлами на диске; запись, файл которой пропал или пуст, удаляется из индекса, и письмо скачивается заново | Удаляются только «висячие» записи индекса. Файлы и письма не трогаются |
| Полностью с нуля | Сначала проверяет вход в ящик; затем каталог писем переименовывается в карантин `account_<номер>_old_<дата-время>`, индекс ящика очищается, и всё скачивается с сервера заново | **Уходит в карантин** («Прежние копии» в меню ящика) и лежит там, пока администратор его не удалит |

Первый режим безопасен и решает обычную задачу «часть файлов потерялась». Второй нужен, когда архив
ящика испорчен и нужен чистый лист. Порядок шагов важен: пока сервер недоступен или пароль сменился,
прежняя копия не трогается вовсе (скачать взамен было бы нечего). Письма, которых уже нет на почтовом
сервере, после пересоздания остаются только в карантине — в просмотре, поиске и экспорте их нет.
Поэтому режим доступен только администратору, требует подтверждения, пишется в аудит и не
повторяется автоматически при сбое; ящики с удержанием архива пересоздать нельзя.

Задание «с нуля», прерванное перезапуском службы или поставленное на повтор после сбоя, прежнюю
копию второй раз не переносит: оно продолжает скачивание, а уже скачанное не качает заново.
«Повторить» у удачно законченного задания «с нуля» пересоздаёт копию заново.

### Прежние копии: сравнение, возврат писем, удаление

После удачной копии «с нуля» прежняя копия **сама сравнивается с новой** — отдельным фоновым
заданием (сравнение читает каждый файл, и на большом ящике это долго). Сравнение читает у каждого
файла прежней копии только блок заголовков, а начало SHA-256 содержимого берёт из имени файла:

| Итог по письму | Что значит |
|---|---|
| есть в новой копии | в новой копии есть письмо с тем же содержимым, и его файл на месте (одних записей индекса мало) |
| другой вариант | тот же Message-ID, тема, отправитель, дата (± сутки) и то же тело письма, но другие заголовки — сервер пересобрал заголовки того же письма |
| только в прежней копии | всё остальное: письма, удалённые на сервере, лежащие в исключённых или неоткрывающихся папках, больше лимита размера, а также письма с чужим содержимым под тем же Message-ID |
| старше срока хранения | «только в прежней», но старше срока хранения ящика — ночная очистка удалила бы их из архива и так |

Письма «только в прежней копии» можно **вернуть в архив** — в те же папки, под особым
UIDVALIDITY, которого не бывает у сервера (копирование их не трогает и заново не скачивает).
Возврат возможен только после того, как копирование хотя бы раз **прочитало все папки** ящика после
«с нуля»: иначе письма ещё не прочитанных папок попали бы в архив дважды. Письма папок, которые
сейчас не открываются на сервере, не возвращаются по той же причине.

**Удалить** прежнюю копию можно, когда сравнение подтвердило, что все её письма есть в новой копии
(или возвращены). Иначе — только с явным подтверждением потери писем. Удаление идёт фоновым
заданием, которое прямо перед удалением сравнивает прежнюю копию с новой ещё раз (файлы новой копии
могли пропасть, срок хранения — измениться); пока по ящику идёт задание, прежние копии не удаляются.

Для многих ящиков сразу — кнопка «🧨 Копия всех с нуля» и групповые действия «Скопировать с нуля»,
«Сравнить прежние копии с новыми», «Вернуть письма из прежних копий», «Удалить прежние копии»
([17-bulk.md](17-bulk.md)).

## Хранилище

Каждое письмо — отдельный файл в формате **Maildir** (стандартные подкаталоги `cur/new/tmp`).
Плюсы: повреждение одного файла не затрагивает остальные; копию легко просматривать, копировать и
переносить; формат понимают многие почтовые программы. Имя файла несёт флаги письма, а UID и
короткий хеш встроены в «уникальную» часть имени.

После записи размер и контрольная сумма (SHA-256) сверяются — защита от «тихой» порчи данных.
Опционально письма сжимаются gzip (экономия места) и **шифруются** AES-256-GCM
([09-encryption.md](09-encryption.md)).

Просмотр, скачивание `.eml` и вложений читают файл **потоком**: письмо в сотни мегабайт не
загружается в память целиком (разбор крупных писем идёт потоковым MIME-парсером — видны текст,
список вложений и сами вложения).

## Хранение и очистка (ретеншн)

Срок хранения локальной копии задаётся двумя способами:

- **у ящика** — меню ящика → «Хранение копий» (3 дня, неделя, «хранить всё», свой срок) или
  шаблон ящиков сотрудников; действует всегда;
- **общий** — «Настройки → Хранение и очистка»: «Хранить дней» применяется к ящикам со сроком
  «как в общих настройках», только когда включена «Общая очистка по сроку».

Очистку раз в сутки запускает планировщик (`retention.cron`, по умолчанию 04:30): задание ставится
каждому ящику, у которого есть что удалять. Удаляются только **локальные** файлы; письма на почтовом
сервере не трогаются. Чтобы следующее копирование не скачало удалённые письма обратно, их UID
запоминаются. Если срок увеличить (или выбрать «хранить всё», или поставить архив на удержание),
эта память сбрасывается, и письма, ещё лежащие на сервере, скачаются заново. Письма старше срока
хранения, которые лежат на сервере, копирование и не скачивает (см. выше). Запись индекса удаляется только вместе с файлом: если
файл удалить не удалось (диск только для чтения и т. п.), письмо остаётся в копии, а задание
завершается «частично» с причиной.

## Обслуживание базы

Раз в сутки служба чистит историю, чтобы база не росла бесконечно: успешные задания старше
30 дней, неудачные — старше 90, журнал попыток входа — старше суток, аудит — старше года,
статистика — старше 5 лет, история восстановлений — старше 180 дней, готовые выгрузки — старше
`export.keep_days` (по умолчанию 30), временные файлы — старше 48 часов. После аварийной остановки
при запуске убираются недописанные выгрузки и временные файлы.

Даты в фильтрах экспорта, аналитике и статистике считаются в часовом поясе `scheduler.timezone`
(по умолчанию Europe/Moscow), а не в UTC.

## Экспорт

Экспорт читает письма из локальной копии и передаёт их выбранному движку:

- **eml/mbox** — прямая запись (без потерь).
- **pst (Aspose)** — через библиотеку Aspose.Email; выбор ANSI/Unicode = выбор поколения Outlook.
- **pst (native)** — собственная реализация формата [MS-PST] в варианте Unicode. Письма сначала
  сбрасываются во временные файлы, затем пишутся папка за папкой: MIME разбирается потоково, и
  вложения любого размера уходят в файл кусками по 8 КБ, не занимая память. Слои формата: NDB
  (блоки с CRC и подписями, деревья XBLOCK/XXBLOCK и подузлов, B-деревья узлов и блоков, карты
  размещения AMap/PMap/FMap, список DList, заголовок), LTP (куча HN, BTH, контексты свойств и
  таблиц) и уровень сообщений: хранилище, обязательные служебные узлы и шаблоны таблиц (как в
  файле, созданном самим Outlook), папки с таблицами иерархии и содержимого, письма с таблицами
  получателей и вложений. `INBOX` становится «Входящими» (папкой входящих хранилища), корзина —
  «Удалёнными», «Отправленные» отмечаются папкой отправленных. Картинки, на которые ссылается HTML
  (`cid:`), скрыты из списка вложений; вложенные письма прикладываются файлами `.eml`. Письмо,
  которое не удалось разобрать, откатывается целиком — в файле не остаётся «брошенных» блоков.
  Часть файла ограничена 1,9 ГБ: крупный ящик пишется в несколько файлов с тем же деревом папок.
  Результат проверяется независимыми читателями: собственным строгим (CRC, подписи, карты
  размещения, кучи, таблицы), libpff и `readpst` (libpst).

## Восстановление

Из локального индекса выбираются письма (с фильтром по папкам/датам), для каждого определяется
целевая папка (та же / с префиксом / одна общая), при необходимости папка создаётся, по желанию
проверяется дубликат по `Message-ID`, и письмо добавляется командой IMAP `APPEND` с сохранением
флагов и даты получения. Есть «сухой прогон» — подсчёт без реальной заливки.

Индекс читается **постранично**, по 5000 записей: архив в миллион писем не нужно целиком держать в
памяти, и ни одно письмо не теряется из-за ограничения выборки.

**Три режима назначения.**

| Режим | Куда попадут письма | Когда выбирать |
|---|---|---|
| В папки с префиксом | `Восстановлено.INBOX`, `Восстановлено.Отправленные`… | по умолчанию: архив не смешивается с текущей почтой |
| Всё в одну папку | одна указанная папка | нужно быстро просмотреть подборку |
| В исходные папки | прямо в рабочие `INBOX`, `Отправленные`… | ящик пуст и его восстанавливают целиком |

Префикс и имя папки обязательны: пустое значение **не** означает «в исходные папки». Раньше
очистка поля «Префикс папки» молча превращала безопасный режим в заливку сотен тысяч писем прямо в
рабочий INBOX живого ящика — отменить это невозможно. Теперь пустое значение отклоняется, а режим
«в исходные папки» требует явного выбора, подтверждения в диалоге и записывается в аудит.

Письма без заголовка `Message-ID` проверить на дубль нечем: они заливаются, но учитываются
отдельно, и в итоге задания выводится предупреждение — при повторном запуске восстановления такие
письма продублируются.

## Импорт .pst

Импорт читает файл данных Outlook — `.pst` или `.ost` — собственной реализацией формата [MS-PST],
парой к встроенному экспорту. Внешние программы не нужны; `readpst` (libpst) остаётся запасным
способом разбора.

**Откуда файл.** Файл либо загружают через интерфейс (до 2 ГБ; он ложится во временный каталог
службы и после импорта удаляется), либо берут из каталога импорта на сервере — `import` в каталоге
данных, куда администратор кладёт файл сам. Такой файл может быть любого размера; служба его
только читает и никогда не удаляет. Имя приходит из браузера, поэтому путь по нему строится в одном
месте и только для обычного файла, лежащего прямо в каталоге импорта: ни путь, ни символическая
ссылка не проходят. Задание помнит не путь, а имя и приметы файла — размер, время изменения, номер
файла на диске — и сверяет их перед каждым запуском: другой файл под тем же именем (почти все они
называются «Outlook.pst») или файл, который ещё копируют, импортирован не будет.

**Чтение файла.** Файл целиком в память не читается. B-дерево блоков обходится по запросу с кэшем
страниц; из B-дерева узлов один раз забираются номера узлов (28 байт на письмо). Дальше — те же
слои, что и при записи, но в обратную сторону: блоки и деревья данных (XBLOCK/XXBLOCK), подузлы
(SLBLOCK/SIBLOCK), куча на узле, B-дерево в куче, контексты свойств и таблиц, а над ними —
хранилище, папки, письма, получатели и вложения. Читаются все три вида файла — ANSI (Outlook
97–2002), Unicode (Outlook 2003 и новее) и Unicode с большими страницами (`.ost` Outlook 2013 и
новее) — и все три способа хранения данных: без кодирования, «сжимаемое шифрование» (так Outlook
создаёт файлы по умолчанию) и «усиленное шифрование».

**Файлы с большими страницами (`.ost` Outlook 2013 и новее).** В [MS-PST] этот вид файла не описан;
его устройство сверено с настоящими файлами. Заголовок у него тот же, что у Unicode, отличия ниже:

- страницы B-деревьев — 4096 байт вместо 512, записей на странице примерно в восемь раз больше;
- блок данных — до 64 КБ (65 512 байт данных) вместо 8 КБ; длинное значение собирается из таких
  блоков теми же деревьями XBLOCK/XXBLOCK;
- блок может быть сжат zlib. Тогда в дереве блоков у него два размера — в файле и после
  распаковки, а контрольная сумма считается по сжатым байтам. Сжаты бывают и блоки данных, и
  служебные;
- распаковка ограничена: из блока достаётся не больше названного в файле размера, а назван может
  быть размер не больше блока. Поток короче или длиннее названного, оборванный или с неверной
  суммой — ошибка этого блока, а не всего файла: блок в сотню байт не развернётся в гигабайты;
- вид файла определяется не по номеру версии в заголовке (у больших страниц он 36), а пробой
  корневой страницы дерева узлов: подходит та раскладка, в которой на своём месте стоит признак
  страницы. Файл с новым номером версии и обычными страницами читается как обычный.

**Корень ящика.** В `.pst` видимые папки начинаются с «Top of Personal Folders» — корень назван в
свойствах хранилища. В `.ost` такого свойства нет: ящик лежит в папке `IPM_SUBTREE` внутри «Root -
Mailbox», рядом — служебные папки и пустое дерево общих папок. Импорт находит эту папку и берёт
только её: служебные папки, общие папки и папки поиска не импортируются. Если папка не нашлась,
импортируется всё дерево файла — лучше лишние папки, чем потерянная почта.

Письма папки перечисляются по связям узлов и, сверх того, по таблице содержимого папки: если одна
из двух структур повреждена, письма находятся по другой.

**Сборка письма.** В `.pst` письмо хранится набором свойств MAPI, поэтому письмо RFC 822
собирается заново:

- заголовки — исходные, если Outlook их сохранил (у полученных писем): остаются `Received`,
  `Message-ID`, подписи DKIM; заголовки о строении тела отбрасываются, потому что тело собирается
  заново. У отправленных писем и черновиков исходных заголовков нет — они составляются из
  свойств: отправитель, получатели «Кому», «Копия» и «Скрытая», тема, дата, важность, цепочка
  ответов. Адресат с внутренним адресом Exchange без адреса SMTP получает адрес-заглушку в домене
  `exchange.invalid` — имя адресата при этом сохраняется. Для отправителя адрес сначала ищется в
  самом письме: тот же адрес Exchange бывает записан рядом с адресом SMTP — у создавшего письмо,
  изменившего его последним, получившего, среди получателей. Совпасть должен адрес Exchange
  целиком; по похожему имени адрес не подставляется;
- тело — текст и HTML; HTML берётся из письма как есть (в исходной кодировке) или достаётся из
  RTF, в который его прячет Outlook; из «настоящего» RTF получается простой текст;
- вложения любого размера кодируются кусками; картинки, на которые ссылается HTML, остаются на
  своих местах; вложенные письма собираются так же и прикладываются как `message/rfc822`;
  подписанные и зашифрованные письма (S/MIME) восстанавливаются в исходном виде;
- флаги («прочитано», «отвечено», «переслано», «помечено», «черновик») и дата получения берутся
  из свойств письма.

Письмо без `Message-ID` (черновик, часть отправленных) получает собственный, выведенный из
содержимого и потому всегда один и тот же. Сборка детерминирована: одно и то же письмо даёт одни и
те же байты.

**Куда попадают письма.**

| Цель | Что происходит | Как узнаётся повтор |
|---|---|---|
| На почтовый сервер | `APPEND` в папки «Префикс/Папка из файла», с флагами и датой получения; при обрыве связи импорт переподключается и продолжает с того же письма | по `Message-ID` среди писем папки назначения (один запрос на папку) |
| В локальную копию | письмо записывается в архив ящика и в индекс как историческое — копирование по IMAP его не трогает и не скачивает заново | по SHA-256 содержимого в той же папке |

Письма старше срока хранения ящика в локальную копию не записываются: их удалила бы ближайшая
ночная очистка. Чтобы импортировать старый архив, поставьте архив ящика на удержание.

**Чужой файл.** Файл приходит от пользователя, поэтому каждое смещение и размер в нём
проверяются, глубина деревьев и объёмы ограничены, а ошибка в одном письме не мешает прочитать
остальные — нечитаемые письма перечисляются в журнале задания. Если в письме не прочиталось
одно вложение, письмо переносится без него, а задание заканчивается «частично». Контрольные суммы
блоков сверяются; несовпадение не останавливает чтение, но считается и попадает в итог задания. Блок,
на который одно дерево данных ссылается больше восьми раз, — ошибка: в настоящих файлах повторов
нет, а в испорченном они превращали один блок в сотни мегабайт чтения. Пароль
файла `.pst` шифрованием не является (его проверяет только сам Outlook) и на чтение не влияет.

Читатель проверяется тестами на файлах, созданных встроенным экспортом, и на тех же файлах,
переложенных в другие виды формата (оба шифрования, ANSI, большие страницы со сжатием), на письмах
с редкими свойствами и на намеренно испорченных файлах. Сверх тестов он прогнан на общедоступных
образцах файлов, созданных Outlook (Unicode и ANSI со «сжимаемым шифрованием», более двух тысяч
писем), — без ошибок чтения.

Файлы с большими страницами проверены на четырёх настоящих `.ost` (от 26 до 40 папок, от 3 до 214
элементов в каждом; большей частью это записи календаря и контакты, писем — около сорока):
контрольные суммы всех страниц и блоков сходятся, размеры после распаковки совпадают с записанными,
вложения совпали с исходными файлами байт в байт. Настоящими файлами **не подтверждено** то, чего в
этих образцах нет:

- куча длиннее одного блока и связанное с ней деление номера записи кучи. По одним описаниям
  формата на номер записи в таких файлах отведено 14 бит, а открытые читатели, с которыми сверялся
  наш, делят его как в обычных файлах — 11 бит. Читатель определяет деление у каждой кучи по её
  же номерам: номер, верный лишь при одном делении, показывает, какое оно (и блок, где записей
  больше 2047, — тоже: при 11 битах он не адресуется). Номер, который при двух делениях указывает
  на разные записи, читается только когда деление кучи известно; иначе элемент не читается и
  попадает в ошибки импорта — подменить данные чужой записью читатель не может;
- уровни XXBLOCK и SIBLOCK в файле с большими блоками;
- сжатие вместе с кодированием данных (все четыре образца — без кодирования);
- `.ost` Outlook 2003–2010: настоящих образцов нет, поиск корня ящика в них проверен на файлах,
  собранных тестами.

Эти случаи читаются по описаниям формата и проверяются только на файлах, которые собирает
тестовый преобразователь самого проекта. Такие тесты ловят расхождение между читателем и
преобразователем, но не ошибку в общем для них представлении о формате. Файлы у всех разные —
перед массовым импортом проверьте импорт на одном своём файле.
