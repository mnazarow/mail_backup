# 2. Методология работы

## Общая архитектура

MailArchiver состоит из взаимодействующих компонентов:

- **Веб-интерфейс (FastAPI)** — управление и мониторинг из браузера, REST API и WebSocket для живых
  обновлений.
- **Очередь заданий** — все тяжёлые операции (бэкап, экспорт, восстановление) выполняются фоновыми
  воркерами; видно прогресс, есть отмена и повторы.
- **Планировщик (APScheduler)** — по расписанию ставит задания в очередь.
- **IMAP-движок** — подключение к почтовым серверам, скачивание и заливка писем.
- **Хранилище (Maildir)** — локальные копии писем на диске.
- **База данных (SQLite)** — индекс писем, задания, настройки, история, пользователи, индекс
  полнотекстового поиска (FTS5).
- **Копия вне сервера** — ежедневно отправляет новые файлы писем и снимки базы в сетевую папку, на
  другой сервер (rsync по SSH) или в S3-хранилище.
- **Мониторинг** — метрики `/metrics` для Prometheus/Zabbix и еженедельная сводка на почту.

```
Веб-интерфейс ─▶ Очередь ─▶ IMAP-движок ─▶ Почтовый сервер
                   │  ▲                └─▶ Хранилище Maildir (.eml)
   Планировщик ────┘  └── База (SQLite): индекс, задания, поиск
                                   │
        Копия вне сервера ◀────────┴── файлы писем + снимки базы ─▶ папка / SSH / S3
```

Фоновые задания, которые ставит сам сервис: копирование по расписаниям, ежедневная очистка по
сроку хранения, индексация поиска (каждые 10 минут, если есть новые письма), копия вне сервера и
снимок базы (раз в сутки), синхронизация сотрудников, обслуживание базы. Тяжёлые служебные задания
(индексация, отчёт об одинаковых вложениях) идут порциями и уступают очередь копированиям ящиков.

## Инкрементальный алгоритм бэкапа

Сервис не скачивает всё заново при каждом запуске. Он опирается на механизмы IMAP:

1. У каждого письма в папке есть уникальный номер **UID**.
2. У папки есть признак **UIDVALIDITY**. Если он изменился, прежний индекс папки считается
   недействительным и папка перечитывается целиком (так требует протокол IMAP).
3. Сервис хранит в БД, какие `(UIDVALIDITY, UID)` уже сохранены, и **докачивает только новые** письма.

Порядок выполнения:

1. Подключение к ящику, получение списка папок, фильтрация по правилам (белый/чёрный списки).
2. **Фаза планирования**: для каждой папки определяются новые письма и общий объём работы (для прогресса).
3. **Фаза загрузки**: письма скачиваются пакетами (UID FETCH), сохраняются в Maildir, заносятся в индекс.
4. Обновление состояния папок и статистики.

Ошибка в одной папке не прерывает весь бэкап — она логируется и учитывается, остальные папки
продолжают копироваться. Обрыв связи посреди копирования не начинает всё заново: сервис
переподключается и продолжает с того же места (подряд — не больше трёх переподключений без
продвижения). Если задание всё же сорвалось (сервер недоступен), оно повторяется с нарастающей
задержкой; отложенный повтор хранится в базе и переживает перезапуск службы.

С одним ящиком одновременно работает **только одно** задание (копирование, очистка, проверка,
перешифровка, экспорт, восстановление) — они не мешают друг другу. При штатной остановке службы
идущие задания возвращаются в очередь и продолжаются после запуска.

Папка, которую сервер не даёт открыть, не считается пропажей писем сразу: несколько прогонов подряд
она помечается «копия неполная» (`backup.unreadable_folder_grace_runs`), а в деталях задания есть
кнопка «Больше не копировать эти папки». Папка-контейнер (в ней нет писем, только подпапки)
пропускается молча.

## Копирование заново

Обычная копия инкрементальная: письмо, уже записанное в индекс, у сервера повторно не запрашивается.
Когда архив нужно перепроверить целиком, в меню ящика есть **«🔄 Скопировать заново»** с двумя
режимами:

| Режим | Что делает | Что удаляется |
|-------|-----------|----------------|
| Докачать потерянные письма | Сверяет индекс с файлами на диске; запись, файл которой пропал или пуст, удаляется из индекса, и письмо скачивается заново | Только «висячие» записи индекса. Файлы и письма не трогаются |
| Полностью с нуля | Стирает локальную копию ящика — файлы писем и записи индекса — и скачивает всё с сервера заново | **Вся локальная копия ящика** |

Первый режим безопасен и решает обычную задачу «часть файлов потерялась». Второй необратим: письма,
которых уже нет на почтовом сервере, есть только в локальной копии, и после стирания их не вернуть.
Поэтому он доступен только администратору, требует подтверждения, пишется в аудит и не повторяется
автоматически при сбое.

## Хранилище

Каждое письмо — отдельный файл в формате **Maildir** (стандартные подкаталоги `cur/new/tmp`).
Плюсы: повреждение одного файла не затрагивает остальные; копию легко просматривать, копировать и
переносить; формат понимают многие почтовые программы. Имя файла несёт флаги письма, а UID и
короткий хеш встроены в «уникальную» часть имени.

После записи размер и контрольная сумма (SHA-256) сверяются — защита от «тихой» порчи данных.
Опционально письма сжимаются gzip (экономия места) и **шифруются** AES-256-GCM
([09-encryption.md](09-encryption.md)).

Просмотр, скачивание `.eml` и вложений читают файл **потоком**: письмо в сотни мегабайт не
загружается в память целиком (разбор крупных писем идёт потоковым MIME-парсером — видны текст,
список вложений и сами вложения).

## Хранение и очистка (ретеншн)

Срок хранения локальной копии задаётся двумя способами:

- **у ящика** — меню ящика → «Хранение копий» (3 дня, неделя, «хранить всё», свой срок) или
  шаблон ящиков сотрудников; действует всегда;
- **общий** — «Настройки → Хранение и очистка»: «Хранить дней» применяется к ящикам со сроком
  «как в общих настройках», только когда включена «Общая очистка по сроку».

Очистку раз в сутки запускает планировщик (`retention.cron`, по умолчанию 04:30): задание ставится
каждому ящику, у которого есть что удалять. Удаляются только **локальные** файлы; письма на почтовом
сервере не трогаются. Чтобы следующее копирование не скачало удалённые письма обратно, их UID
запоминаются. Если срок увеличить (или выбрать «хранить всё»), эта память сбрасывается, и письма,
ещё лежащие на сервере, скачаются заново. Запись индекса удаляется только вместе с файлом: если
файл удалить не удалось (диск только для чтения и т. п.), письмо остаётся в копии, а задание
завершается «частично» с причиной.

## Обслуживание базы

Раз в сутки служба чистит историю, чтобы база не росла бесконечно: успешные задания старше
30 дней, неудачные — старше 90, журнал попыток входа — старше суток, аудит — старше года,
статистика — старше 5 лет, история восстановлений — старше 180 дней, готовые выгрузки — старше
`export.keep_days` (по умолчанию 30), временные файлы — старше 48 часов. После аварийной остановки
при запуске убираются недописанные выгрузки и временные файлы.

Даты в фильтрах экспорта, аналитике и статистике считаются в часовом поясе `scheduler.timezone`
(по умолчанию Europe/Moscow), а не в UTC.

## Экспорт

Экспорт читает письма из локальной копии и передаёт их выбранному движку:

- **eml/mbox** — прямая запись (без потерь).
- **pst (Aspose)** — через библиотеку Aspose.Email; выбор ANSI/Unicode = выбор поколения Outlook.
- **pst (native)** — встроенная реализация подмножества формата MS-PST (ANSI): заголовок, слои NDB
  (BTree узлов и блоков) и LTP (куча HN, BTH, контекст свойств PC), дерево папок по полю `nidParent`.
  Результат проверяется на чтение утилитой `readpst` (libpst). Вложения этим движком не переносятся —
  только папки, тема, адреса, дата и текст писем.

## Восстановление

Из локального индекса выбираются письма (с фильтром по папкам/датам), для каждого определяется
целевая папка (та же / с префиксом / одна общая), при необходимости папка создаётся, по желанию
проверяется дубликат по `Message-ID`, и письмо добавляется командой IMAP `APPEND` с сохранением
флагов и даты получения. Есть «сухой прогон» — подсчёт без реальной заливки.

Индекс читается **постранично**, по 5000 записей: архив в миллион писем не нужно целиком держать в
памяти, и ни одно письмо не теряется из-за ограничения выборки.

**Три режима назначения.**

| Режим | Куда попадут письма | Когда выбирать |
|---|---|---|
| В папки с префиксом | `Восстановлено.INBOX`, `Восстановлено.Отправленные`… | по умолчанию: архив не смешивается с текущей почтой |
| Всё в одну папку | одна указанная папка | нужно быстро просмотреть подборку |
| В исходные папки | прямо в рабочие `INBOX`, `Отправленные`… | ящик пуст и его восстанавливают целиком |

Префикс и имя папки обязательны: пустое значение **не** означает «в исходные папки». Раньше
очистка поля «Префикс папки» молча превращала безопасный режим в заливку сотен тысяч писем прямо в
рабочий INBOX живого ящика — отменить это невозможно. Теперь пустое значение отклоняется, а режим
«в исходные папки» требует явного выбора, подтверждения в диалоге и записывается в аудит.

Письма без заголовка `Message-ID` проверить на дубль нечем: они заливаются, но учитываются
отдельно, и в итоге задания выводится предупреждение — при повторном запуске восстановления такие
письма продублируются.
