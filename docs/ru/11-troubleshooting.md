# 11. Устранение неполадок

## Диагностика

- Логи службы: `journalctl -u mailarchiver -n 100 --no-pager` (или раздел «Логи» в интерфейсе).
- Проверка конфигурации: `sudo mailarchiver check-config` (опечатки в именах параметров выводятся
  предупреждениями, неверные значения — ошибкой с подсказкой). Команда смотрит и на каталоги: если
  каталог данных недоступен — например это ссылка на неподключённый диск, — она скажет об этом и
  завершится с ошибкой.
- Проверка перед обновлением, ничего не меняя: `sudo bash scripts/update.sh --check` из каталога с
  новой версией ([03-installation.md](03-installation.md), раздел «Обновление»).
- Для подробностей временно поднимите уровень логирования до `DEBUG` (Настройки → Логирование) —
  применяется сразу, без перезапуска.
- Состояние шифрования копии: `sudo mailarchiver storage-key`.
- Работа с базой из консоли (`sqlite3`) — установите утилиту: `sudo apt install sqlite3`
  (RHEL: `sudo dnf install sqlite`).

## Частые проблемы

| Симптом | Причина и решение |
|---------|-------------------|
| «Аутентификация IMAP не удалась» | Неверный логин/пароль, либо нужен «пароль приложения»/OAuth2. Включите IMAP в настройках почты, создайте пароль приложения. |
| «Ошибка TLS/SSL» | Неверный порт/режим шифрования. SSL — порт 993, STARTTLS — порт 143. Для самоподписанного сертификата отключите проверку сертификата. |
| «Превышено время ожидания» | Медленная сеть/сервер. Увеличьте `backup.socket_timeout_s` и `backup.connect_timeout_s`. |
| «Не удалось соединиться с IMAP-сервером» | Проверьте адрес хоста, порт, доступность сервера и файрвол. |
| Бэкап идёт слишком медленно | Увеличьте `backup.fetch_batch_size`; проверьте лимиты почтового сервера. |
| Экспорт `.pst` не открывается в Outlook | Встроенный движок пишет формат Unicode — нужен Outlook 2003 или новее. Если файл всё же не открывается, пришлите журнал задания экспорта и временно используйте Aspose (с лицензией) или экспорт EML/MBOX. |
| `.pst` разбит на несколько файлов | Встроенный движок делит ящик на части до 1,9 ГБ (или по размеру из «Разбивать PST по, МБ»). Подключите в Outlook каждый файл: «Файл → Открыть и экспортировать → Открыть файл данных Outlook». |
| Импорт `.pst`: «Файл не разобран» | Это не файл данных Outlook: у файла нет его подписи, это файл другого назначения (например автономная адресная книга) или его устройство импорту неизвестно — причина названа в сообщении. Файлы `.pst` и `.ost` всех версий Outlook, включая `.ost` Outlook 2013 и новее, встроенный разбор читает. Проверьте файл; если он открывается в Outlook, выберите в окне импорта «Дополнительно → Способ разбора файла → readpst» (нужен пакет: Debian/Ubuntu — `sudo apt install pst-utils`, RHEL — `sudo dnf install libpst`). |
| Импорт `.pst`: «Файл .pst повреждён и не читается» | Файл обрезан при копировании или повреждён. Проверьте его средством восстановления Outlook (`scanpst.exe`) и загрузите заново. Отдельные нечитаемые письма импорт пропускает сам — они перечислены в журнале задания. Для файла из каталога импорта самая частая причина другая: импорт запустили, пока файл ещё копировался на сервер, — дождитесь конца копирования (сверьте размер с исходным файлом) и запустите импорт заново. |
| Импорт `.pst`: «Файл слишком большой» | Через браузер передаётся файл до 2 ГБ. Положите файл в каталог импорта на сервере и выберите в окне импорта «Взять с сервера» — так импортируется файл любого размера ([10-mailboxes.md](10-mailboxes.md), раздел «Импорт из .pst»). |
| Файла нет в списке «Файл на сервере» | В списке — только обычные файлы `.pst` и `.ost`, лежащие прямо в каталоге импорта (`/var/lib/mailarchiver/import`). Не показываются файлы во вложенных каталогах, символические ссылки, пустые файлы и файлы с именем, начинающимся с точки. Положите в каталог сам файл и нажмите «Обновить список». |
| В списке «Файл на сервере» пометка «нет доступа у службы»; «Служба не может прочитать файл … нет прав» | Файл положен от root и принадлежит не службе. Отдайте его пользователю службы: `sudo chown mailarchiver: /var/lib/mailarchiver/import/ФАЙЛ.pst` (точная команда показана под списком) и нажмите «Обновить список». |
| Окно импорта: «каталог импорта недоступен»; задание: «Каталог импорта на сервере сейчас недоступен» | Службе не виден каталог `import` в каталоге данных: его нет, он закрыт для пользователя службы или это ссылка на диск, который не подключён. Причина и команда, которая её устранит, написаны в окне импорта под списком «Файл на сервере». Каталог в `/home`, `/root` и `/tmp` служба не видит при любых правах. После исправления нажмите «Обновить список», а у задания — «Повторить». Загрузка файла с компьютера при этом работает. |
| Импорт: «Файл … не найден в каталоге импорта» | Между постановкой задания и запуском (или к моменту «Повторить») файл убрали или переименовали. Положите его на место под тем же именем и нажмите «Повторить» — либо запустите импорт заново. |
| Импорт: «Файл … в каталоге импорта изменился после постановки задания — запустите импорт заново» | Под этим именем лежит уже не тот файл, что выбирали: его заменили другим или он в ту минуту ещё копировался (в подсказке сказано, что изменилось — размер, время изменения или сам файл). Задание намеренно не берёт «другой файл с тем же именем». Дождитесь конца копирования и запустите импорт заново: «Импорт из .pst» → «Взять с сервера». |
| Импорт закончился «частично»: «Файл в каталоге импорта менялся, пока шёл импорт» | Файл дописывали во время импорта — скорее всего, его ещё копировали на сервер, и письма могли попасть не все. Когда копирование закончится, запустите импорт заново: уже перенесённые письма второй раз не запишутся. |
| «Импорт файлов с сервера отключён: каталог импорта пересекается с каталогом временных файлов службы» | Каталог импорта сделан ссылкой на каталог, внутри которого лежат временные файлы службы (например на весь диск с данными), либо `export.tmp_dir` направлен в каталог импорта. Временные файлы служба удаляет сама, а в каталоге импорта не трогает ничего — вместе это не работает. Направьте ссылку на отдельный каталог только для файлов `.pst` и `.ost` или задайте другой `export.tmp_dir`; точная команда — в окне импорта. Остальная работа службы не затронута. |
| После импорта вместо русских букв «кракозябры» | Старый файл ANSI (Outlook 97–2002) в другой кодировке. Повторите импорт с другой кодировкой: «Дополнительно → Кодировка старых файлов (ANSI)». Для файлов Outlook 2003 и новее настройка не нужна. |
| Импорт в локальную копию: «Старше срока хранения — не записано» | У ящика задан срок хранения локальных копий, а письма в файле старше него: ночная очистка удалила бы их. Поставьте архив ящика на удержание или задайте «хранить всё» и повторите импорт. |
| Импорт остановился: «связь с сервером потеряна» или «кончилось место в ящике» | Устраните причину и нажмите «Повторить» у задания: загруженный файл хранится на сервере до 48 часов (или до перезапуска службы), уже залитые письма второй раз не зальются. Если файла уже нет («Файл .pst для импорта не найден»), загрузите его заново. Файл из каталога импорта служба не удаляет — «Повторить» для него работает, пока файл на месте. |
| Импорт закончился «частично»: «перенесено с потерями» | В части писем не прочиталось вложение или тело — файл повреждён в этих местах. Письма названы в журнале задания; сами письма перенесены, но без нечитаемой части. Возьмите исправную копию файла или прогоните его через `scanpst.exe` и повторите импорт. |
| В итоге импорта «в файле блоков с неверной контрольной суммой» | Файл повреждён (обычно при копировании по сети или на сбойном диске). Письма из таких блоков могли исказиться — возьмите исправную копию файла или прогоните его через `scanpst.exe`. |
| Служба не запускается | Смотрите `journalctl -u mailarchiver -n 50`. Частые причины: занят порт, ошибка в `config.yaml`, нет прав на каталог данных, не подключён диск с каталогом данных или каталог перенесли, а ссылку не поправили (см. «Каталог данных недоступен» ниже). |
| Обновление закончилось откатом: «Служба не запустилась» | Скрипт печатает причину — последние строки журнала службы и пояснение. Если обновляли скриптом до 1.9.1 и причины в выводе нет, посмотрите её в журнале: `journalctl -u mailarchiver --since "-1h" --no-pager \| grep -iE "CHDIR\|EXEC\|NAMESPACE\|Error\|failed"`. |
| В журнале `status=200/CHDIR`, «Changing to the requested working directory failed» | Служба не может войти в свой рабочий каталог `/opt/mailarchiver/app`. Так было при обновлении из архива 1.9.0 (права 0700/0600) — возьмите архив 1.9.1 или новее. Если закрыт каталог выше (например `/opt`), откройте его: `namei -l /opt/mailarchiver/app` покажет какой, `chmod o+x КАТАЛОГ` исправит. |
| В журнале `status=226/NAMESPACE` | systemd не смог собрать защищённое окружение службы; до самой программы дело не дошло. Причину называет конец строки «Failed to set up mount namespacing: …» в `journalctl -u mailarchiver`: «No such file or directory» — нет каталога, нужного службе (следующая строка таблицы); «Permission denied» — контейнер без вложенности (строка за ней). Скрипты установки и обновления разбирают это сами и печатают, что делать. |
| `status=226/NAMESPACE` и «… No such file or directory» | Нет каталога из `ReadWritePaths` — каталога данных. Чаще всего он лежит на другом диске (или это ссылка на него), а диск не подключён или пул ZFS не импортирован; бывает и так, что каталог перенесли, а ссылку не поправили. Проверьте: `ls -ld /var/lib/mailarchiver; findmnt; lsblk`, подключите диск (`sudo mount -a`) или направьте ссылку на перенесённый каталог (`sudo ln -sfn НАСТОЯЩИЙ_КАТАЛОГ /var/lib/mailarchiver`), убедитесь, что данные на месте (`ls /var/lib/mailarchiver/`), затем `sudo systemctl reset-failed mailarchiver; sudo systemctl start mailarchiver`. Каталог не создавайте и владельца не меняйте — см. «Каталог данных недоступен» ниже. |
| `status=226/NAMESPACE` и «… Permission denied» | Сервер — контейнер LXC или OpenVZ без вложенности: systemd не может создать для службы пространство имён. Включите вложенность у контейнера (Proxmox: `pct set <ID> --features nesting=1`) либо повторите установку или обновление с ослабленной защитой: `sudo MA_RELAX_SANDBOX=1 bash scripts/update.sh`. Что при этом отключается и как вернуть полную защиту — [03-installation.md](03-installation.md), раздел «Контейнеры LXC и OpenVZ». |
| `FileExistsError: [Errno 17] File exists: '/var/lib/mailarchiver'` или «ОШИБКА: File exists: /var/lib/mailarchiver» (версии до 1.10.0) | Каталог данных — символическая ссылка на каталог, которого сейчас нет: не подключён диск с данными. С версии 1.10.0 программа пишет это прямо: «ОШИБКА: Каталог данных … — ссылка на …, а такого каталога сейчас нет». Что делать — «Каталог данных недоступен» ниже. |
| Обновление или проверка: «Каталог данных … — ссылка на …, а такого каталога сейчас нет», «…лежит на неподключённом диске», «Нет каталога данных …» | Скрипт остановился до остановки службы: с таким каталогом данных не запустится никакая версия. Если скрипт пишет «База службы (mailarchiver.db) нашлась в другом месте» — каталог данных перенесли, а путь не поправили: выполните названную им команду `ln -sfn …`. Иначе подключите диск — «Каталог данных недоступен» ниже. |
| Проверка: «В каталоге данных нет базы …» | Каталог данных есть, а файла базы в нём нет: служба ещё ни разу не запускалась либо это не тот каталог — например пустая точка монтирования, диск под которой не подключён. Проверьте `ls /var/lib/mailarchiver/` и `findmnt`. Если каталог не тот — подключите диск или задайте `MA_DATA_DIR`; если базы и не должно быть — `sudo bash scripts/update.sh --force`. |
| Проверка: «Служба не работает уже сейчас, до обновления»; после отката: «До обновления служба тоже не работала…» | Служба падала ещё до обновления — под сообщением последние строки её журнала. Обновление это исправит, только если причина в самой программе; если нет каталога данных или занят порт, сначала устраните причину. |
| Проверка: «Новые исходники (…) лежат внутри каталога установки …» | Архив новой версии распакован внутрь `/opt/mailarchiver/app`: при обновлении содержимое этого каталога заменяется. Распакуйте архив в другой каталог (например в `/root`) и запустите `scripts/update.sh` оттуда. |
| Проверка: «Python окружения не запускается», «pip окружения не запускается» | Так бывает после обновления Python в системе: окружение службы ссылается на интерпретатор, которого больше нет. Пересоздайте окружение установкой поверх: `sudo bash scripts/install.sh` из каталога с исходниками (данные и конфигурация не трогаются). |
| Проверка: ⚠ «Индекс пакетов … не отвечает» | У сервера нет доступа к PyPI: pip не загрузит библиотеки — уже после остановки службы. Если у pip есть прокси или кэш, которых проверка не видит, предупреждение можно не учитывать. Если в сети есть зеркало — `sudo MA_INDEX_URL=https://зеркало/simple/ bash scripts/update.sh`; если доступа нет вовсе — соберите автономный архив ([03-installation.md](03-installation.md), раздел «Установка и обновление без интернета»). |
| Проверка: «Обновление без сети не пройдёт: pip не может установить пакеты из …» | В каталоге `wheels` нет пакетов под Python сервера: автономный архив собран под другую версию Python, другую архитектуру или более новую систему либо неполон. Соберите его на машине с той же версией Python и той же архитектурой: `bash scripts/make_offline_bundle.sh`. |
| Проверка: «Новая версия не принимает конфигурацию …» | Под сообщением — ответ `check-config` новой версии: исправьте названный параметр в `config.yaml` и повторите. Служба пока работает на прежней версии. Если причина не в конфигурации и после установки проверка всё равно повторится — `--force`. |
| Скрипт ответил «Неизвестный параметр: …» | У `install.sh` параметров нет, у `update.sh` — `--check` и `--force`, у `uninstall.sh` — `--purge` и `--remove-user`. Справка: `bash scripts/update.sh --help`. Переменные `MA_*` пишутся после `sudo`: `sudo MA_START_TIMEOUT=900 bash scripts/update.sh`. |
| Обновление «висит» после «Конфигурация корректна ✓», веб-интерфейс не открывается (скрипт версий 1.10.0–1.11.1) | Скрипт не завис: он молча проверяет владельца каждого файла каталога данных, а служба в это время остановлена. Когда каталог данных — ссылка на другой диск, на сотнях тысяч писем это десятки минут. Проверьте во втором окне: `ps -ef --forest \| grep -A3 '[u]pdate.sh'` — там будет `find … -exec chown`; `ls -l /proc/$(pgrep -nx find)/fd \| grep mailboxes` показывает, где обход сейчас (повторите через минуту — путь сменится). Дождитесь конца или нажмите Ctrl-C: обновление откатится, прежняя версия запустится, база не тронута. С версии 1.11.2 обход идёт до остановки службы и раз в 30 секунд пишет, сколько файлов проверено. |
| Обновление остановилось: «порт занят другим процессом» | Служба остановлена, а её адрес отвечает — на порту работает что-то ещё, обычно `mailarchiver`, запущенный вручную (в `screen`, из консоли). Найдите процесс: `ss -ltnp \| grep 8493` — и остановите его, затем повторите обновление. |
| Обновление ждёт три минуты и откатывается: «веб-интерфейс так и не ответил» | С версии 1.11.2 так бывает, только если служба за это время перестала что-либо делать — скрипт пишет «Служба при этом уже ничего не делала… похоже, зависла»: причину ищите в журнале службы под сообщением. Занятую службу (первый запуск обновляет базу) скрипт ждёт дальше, до часа. Скриптом 1.11.1 и старше на большом архиве дайте больше времени: `sudo MA_START_TIMEOUT=900 bash scripts/update.sh`. Если служба слушает нестандартный адрес (свой `ExecStart` в дополнении к unit), задайте его: `MA_HEALTH_URL=http://адрес:порт/health`. |
| Обновление откатывается: «Служба занята уже … — дольше предела MA_START_TIMEOUT_MAX» | Служба больше часа что-то делала, но веб-интерфейс так и не поднялся. Если база очень большая — дайте больше времени: `sudo MA_START_TIMEOUT_MAX=14400 bash scripts/update.sh`; если нет — посмотрите, чем она занята, в журнале службы под сообщением. |
| «Недостаточно места на диске» | Включите ретеншн (`retention.keep_days`) или сжатие писем (`storage.compress`), либо расширьте диск. |
| Не открывается веб-интерфейс снаружи | По умолчанию слушает `127.0.0.1`. Настройте reverse proxy с HTTPS или используйте SSH-туннель. |
| Не приходят уведомления | Проверьте параметры SMTP (хост, порт, шифрование, логин/пароль) и что включено «Уведомлять об ошибках». |
| WebSocket не обновляет дашборд (за прокси) | В reverse proxy пробросьте заголовки `Upgrade`/`Connection` (см. пример nginx в полной документации). |
| Пустая страница и `500` при открытии интерфейса, в логе `unhashable type: 'dict'` | Несовместимая версия библиотеки Starlette. См. раздел «Ошибки из-за версий библиотек» ниже. |
| `Не удалось установить зависимости Python` при установке | Чаще всего — слишком новый Python, под который ещё нет готовых пакетов. См. «Ошибки из-за версий библиотек». |
| «Пропуск папки … failed EXAMINE», «КОПИЯ НЕПОЛНАЯ» | Почтовый сервер не даёт открыть папку. См. раздел «Папка не открывается: failed EXAMINE» ниже. |
| «Сервер вернул папку … повторно» | Сервер прислал одну и ту же папку в списке дважды. Вторая запись отбрасывается, копия не задваивается — делать ничего не нужно. |
| Ящик в отборе «С неправильным паролем» | Сервер отверг логин или пароль. Исправьте пароль (карточка ящика или «Загрузить пароли») и нажмите «Проверить пароли». «Пароль не читается» — заменён файл `secret.key`: введите пароль заново. |
| Красная плашка «Копирование остановлено: нет ключа шифрования» | Шифрование включено, а файл ключа не найден или не подходит. Верните ключ на место и перезапустите службу — см. [09-encryption.md](09-encryption.md). |
| «Письмо зашифровано, а ключ шифрования не загружен» | То же: без ключа зашифрованные письма не открыть. |
| «Слишком много неверных кодов … ввод кодов из приложения заблокирован» | Кто-то подбирает код 2FA — значит, пароль учётной записи, скорее всего, известен постороннему. Войдите резервным кодом и смените пароль. |
| «Код из приложения сейчас проверить нельзя: секрет … не расшифровывается» | Заменён или утерян `secret.key`. Войдите резервным кодом либо отключите 2FA: `sudo mailarchiver reset-2fa -u ИМЯ`. |
| «Время на ввод кода истекло или попытки исчерпаны» | На один вход даётся 5 минут и 3 попытки ввода кода. Введите пароль ещё раз. Проверьте, что часы телефона выставлены автоматически. |
| «Слишком много неудачных попыток входа в этот ящик» / «Вход по паролю почтового ящика временно приостановлен» | Сработала защита от подбора паролей почты через страницу входа. Подождите `lockout_minutes` (по умолчанию 15 минут). |
| При первичной настройке: «Запрос пришёл на незнакомое имя сервера» (код 421) | Откройте интерфейс по IP-адресу или `http://127.0.0.1:8493` (SSH-туннель) либо укажите имя в `server.public_url`. |
| «Сеанс завершён» и форма входа | Истёк срок сеанса или тайм-аут бездействия, либо пароль сменили в другом месте. Войдите снова — откроется тот же раздел. |
| Синхронизация сотрудников: «Ящики не заведены: в шаблоне ящиков не указан IMAP-сервер» | Укажите сервер в «Сотрудники → Шаблон ящиков» (или `employees.account_host`) и запустите синхронизацию ещё раз. |
| «Выгрузка получена не целиком» при синхронизации сотрудников | Соединение с источником оборвалось — частичный список не применяется. Повторите позже или увеличьте «Таймаут загрузки». |
| «Выгрузка отмечает уволенными N сотрудников … увольнения НЕ применены» | Сработала защита от испорченной выгрузки (больше 20 % работающих разом). Проверьте файл. Если увольнения настоящие — отметьте сотрудников вручную или временно выключите «Отмечать уволенных по выгрузке». |
| Поиск не находит письмо, которое точно есть | Индекс ещё строится (над строкой поиска — «Проиндексировано N из M»), либо при шифровании копии текст писем не индексируется — ищите по теме, адресам, именам вложений. См. [15-search.md](15-search.md). |
| `/metrics` отвечает 404 | Метрики выключены: «Настройки → Мониторинг → Метрики для Prometheus и Zabbix». |
| `/metrics` отвечает 401 или 403 | Запрос не с разрешённого адреса и без верного токена. Передайте заголовок `Authorization: Bearer ТОКЕН` или добавьте адрес сервера мониторинга в «Адреса без токена». |
| «Вход через учётную запись администратора почты отклонён сервером» | Неверный логин/пароль администратора, не тот способ входа или сервер не умеет такой вход (Axigen). См. [16-mailadmin.md](16-mailadmin.md). |

## Папка не открывается: `failed EXAMINE`

В журнале задания: «Пропуск папки «Отправленные/s2022»: … select failed: failed EXAMINE».
Это ответ **почтового сервера** — он отказался открыть папку. MailArchiver в этом случае:

1. повторяет попытку через полторы секунды (часть отказов временная — ящик занят другой сессией);
2. пробует открыть папку обычным `SELECT` вместо `EXAMINE` — некоторые серверы (замечено на Axigen)
   отказывают только на `EXAMINE`. Письма всё равно скачиваются командой `BODY.PEEK`, поэтому
   отметки «прочитано» на сервере не появляются;
3. проверяет, есть ли у папки **вложенные папки**. Если есть — это папка-контейнер: своих писем она
   не хранит (сервер просто не пометил её флагом `\Noselect`), вложенные копируются отдельно, и
   копия остаётся полной;
4. если не вышло — спрашивает сервер командой `STATUS`, **сколько писем он видит в этой папке**:
   - `0 писем` — копия остаётся **полной**, в журнале появляется строка «папка ПУСТАЯ … потерь нет».
     Так выглядят битые пустые папки, оставшиеся на сервере;
   - `N писем` — задание помечается «частично выполнено», а в итоге пишется «КОПИЯ НЕПОЛНАЯ»
     с перечнем папок: эти письма в архив не попали.

### Папка не открывается давно: сервис перестаёт считать это ошибкой

Папка, которую сервер не отдаёт **несколько прогонов подряд**, переходит в разряд «известных
нечитаемых»: сервис продолжает пробовать её каждый раз и продолжает писать о ней в итоге задания,
но задание больше не помечается неполным. Сколько прогонов терпеть, задаёт настройка
**«Терпеть нечитаемую папку, прогонов»** (Настройки → «Резервное копирование», по умолчанию 3;
`0` — считать ошибкой всегда).

Зачем так: папку, сломанную на почтовом сервере, из архива не починить, а вечное «КОПИЯ НЕПОЛНАЯ»
приучает не читать предупреждения — и следующая настоящая пропажа писем остаётся незамеченной.
В журнале это видно по строкам: сначала «…ещё 2 — и папка перейдёт в «известные нечитаемые»»,
потом «не открывается 4-й прогон подряд, с 21.09.2026 — ошибкой больше не считаем». Как только
сервер отдаст папку, счётчик сбрасывается и письма копируются как обычно.

Всё, что сервис пробовал и узнал, попадает в текст ошибки, например:

```
Не удалось открыть папку «Отправленные/s2022»: …
Что пробовали: EXAMINE — отказ (попыток: 2); обычный SELECT — отказ (failed SELECT).
Дополнительно: на команду STATUS сервер тоже не ответил; в списке папок сервера это имя
есть (LIST по точному имени находит его) — значит имя верное, а сама папка на сервере нерабочая.
```

Две строки «Дополнительно» отвечают на главный вопрос — кто виноват:

| Что написано | Что это значит |
|--------------|----------------|
| «в списке папок сервера это имя есть … сама папка нерабочая» | Имя мы шлём правильное, сервер его признаёт, но папку не отдаёт. Чинить на почтовом сервере. |
| «LIST по точному имени эту папку НЕ находит» | Сервер не признаёт это имя своим: беда с кодировкой или невидимым символом. Сервис дополнительно назовёт найденный символ (например «невидимый символ NBSP (U+00A0)»). |
| «по команде STATUS сервер сообщает: писем N» | Столько писем не попало в копию — масштаб потери. При `0` копия остаётся полной. |

### Кнопка «Проверить папки на сервере»

«Почтовые ящики» → «⋯» у нужного ящика → **«🗂️ Проверить папки на сервере»** (сразу для многих
ящиков — групповое действие «🩺 Проверить папки на сервере»: итог по каждому ящику в карточке
задания). Сервис опрашивает КАЖДУЮ папку и показывает таблицу с вердиктом по каждой:

| Вердикт | Что значит |
|---------|------------|
| копируется | Папка открывается, письма доступны |
| контейнер | Папка не открывается, но у неё есть вложенные папки: своих писем она не хранит, содержимое копируется через вложенные. Потерь нет |
| контейнер (`\Noselect`) | Сервер сам пометил папку как неоткрываемую |
| пустая, не открывается | Не открывается, но по `STATUS` писем 0 — терять нечего |
| **НЕ ЧИТАЕТСЯ** | Не открывается, письма недоступны. **Вот это и есть потеря** — вверху показано, сколько писем |
| исключена | Папка не копируется по настройкам ящика |

Внизу — кнопка «🚫 Больше не копировать эти папки» для нечитаемых.

Что проверить на почтовом сервере:

- **Открывается ли папка в веб-почте.** Если и там не открывается — дело не в MailArchiver.
- **Имя папки.** Имена вида `s2022` и `s2022_000` рядом — признак того, что сервер сам создал
  дубликат при конфликте имён (в файловой системе `s2022` и `S2022` — одно и то же). Такие папки
  обычно и не открываются: их удаляют или переименовывают на сервере.
- **Права (ACL)** учётной записи на эту папку и **не заблокирован ли ящик** другой сессией.
- **Axigen**: починить учётную запись можно через CLI (`telnet 127.0.0.1 7000` → `update domain
  name <домен>` → `REPAIR Accounts <учётка>`). Учтите: восстановленная копия создаётся под именем
  вида `<учётка>.00000015.repaired` и её нужно переименовать, поэтому это крайняя мера —
  делайте её в окно обслуживания и с резервной копией.
- Если папку на сервере не починить, добавьте её в **«Пропускать папки»**. Быстрее всего — из
  карточки задания: «Очередь и задания» → «Детали» → блок «Копия неполная» → кнопка
  **«🚫 Больше не копировать эти папки»**. Она добавит перечисленные папки в исключения ящика;
  убрать их можно в карточке ящика. Так задание перестанет помечаться неполным из-за папок,
  которые всё равно не восстановить, — и следующая настоящая пропажа писем будет заметна.

## Каталог данных недоступен: диск не подключён или каталог перенесли

Каталог данных (`/var/lib/mailarchiver`) часто выносят на другой диск: называют его при установке
или делают ссылкой на каталог другого диска. Если диск не подключён (после перезагрузки, сбоя
монтирования) или каталог перенесли, а ссылку не поправили, служба не запускается — ни новая
версия, ни прежняя. Как это выглядит:

| Где | Что видно |
|-----|-----------|
| `systemctl status mailarchiver`, `journalctl -u mailarchiver` | `status=226/NAMESPACE`, «Failed to set up mount namespacing: … No such file or directory» |
| `sudo mailarchiver check-config` и другие команды, версия 1.10.0 и новее | «ОШИБКА: Каталог данных … — ссылка на …, а такого каталога сейчас нет» и подсказка проверить, подключён ли диск |
| те же команды в версиях до 1.10.0 | «ОШИБКА: File exists: /var/lib/mailarchiver»; `check-config` при этом отвечал «Конфигурация корректна ✓» |
| `update.sh`, `update.sh --check` и `install.sh` версии 1.10.0 и новее | отказ до остановки службы: «Каталог данных … — ссылка на …, а такого каталога сейчас нет» или «Каталог данных … лежит на неподключённом диске — файловая система … из /etc/fstab не подключена» |
| `update.sh` версии 1.9.1 | обновление доходило до шага «пробный импорт веб-приложения», обрывалось трассировкой Python со строкой `FileExistsError: [Errno 17] File exists: '/var/lib/mailarchiver'` и откатывалось; прежняя версия после отката не запускалась (`226/NAMESPACE`) |

Проверить и исправить:

```bash
ls -ld /var/lib/mailarchiver              # ссылка? куда она ведёт
readlink -m /var/lib/mailarchiver         # настоящий каталог, даже если его сейчас нет
findmnt; lsblk; grep -v '^#' /etc/fstab   # что подключено и что должно быть подключено
sudo mount -a                             # или: sudo mount /точка/монтирования
ls /var/lib/mailarchiver/                 # данные на месте: mailarchiver.db, mailboxes/ …
sudo systemctl reset-failed mailarchiver; sudo systemctl start mailarchiver
```

**Пул ZFS не импортирован.** Так было на одном сервере: `/var/lib/mailarchiver →
/storage/storage/mailarchiver/`, каталоги `/storage` и `/storage/storage` есть, но пусты, в
`/etc/fstab` — только системный диск, а `lsblk -f` показывает у раздела `zfs_member` с меткой
`storage` — это имя пула. Пул не импортировался после перезагрузки, его точки монтирования
остались пустыми каталогами. Скрипт обновления с версии 1.11.1 называет такой пул сам. Вручную:

```bash
lsblk -f                                   # FSTYPE zfs_member, LABEL — имя пула
sudo zpool import                          # пулы, доступные для импорта
sudo zpool import storage; sudo zfs mount -a
ls -la /var/lib/mailarchiver/              # mailarchiver.db, secret.key, mailboxes/
sudo systemctl reset-failed mailarchiver; sudo systemctl restart mailarchiver
```

Чтобы пул подключался сам и служба его дожидалась — [03-installation.md](03-installation.md),
раздел «Каталог данных на отдельном диске», абзац «Пул ZFS». «pool was previously in use from another
system» в ответ на `zpool import` — `zpool import -f storage`, но только если диск больше нигде не
подключён.

**Каталог перенесли, а ссылка ведёт не туда.** Служба, работавшая во время переноса, продолжает
работать с уже открытым каталогом и падает только при перезапуске — обычно при обновлении. Скрипт
обновления с версии 1.11.1 сам ищет базу рядом с целью ссылки и в обычных местах для данных и
печатает готовую команду. Вручную:

```bash
ls -la /storage /storage/storage          # что лежит рядом с целью ссылки
sudo find / \( -path /proc -o -path /sys -o -path /run -o -path /dev \) -prune -o -name mailarchiver.db -print
sudo ln -sfn /storage/mailarchiver /var/lib/mailarchiver     # каталог, где mailarchiver.db, secret.key, mailboxes/
ls -la /var/lib/mailarchiver/
sudo systemctl reset-failed mailarchiver; sudo systemctl restart mailarchiver
```

`ln -sfn` меняет только саму ссылку, данные не перемещаются. Каталог с `secret.key` рядом с базой —
настоящий: без этого файла не расшифруются пароли ящиков.

Пока диск не подключён и данные не найдены, **не создавайте каталог и не меняйте его владельца**. Неподключённый диск
выглядит как пустой каталог, принадлежащий root, — это сама точка монтирования. Служба запустилась
бы на нём как только что установленная: с новой, пустой базой, без ящиков и расписаний. Скрипты
такого совета и не дают, если точка монтирования записана в `/etc/fstab`; диск, который
подключается иначе, они распознать не могут.

Обновление после этого повторите как обычно. Незавершённая попытка ничего не испортила: проверка
отказывает до остановки службы, а откат версии 1.9.1 вернул прежние код и окружение.

Чтобы служба не запускалась раньше диска после перезагрузки —
[03-installation.md](03-installation.md), раздел «Каталог данных на отдельном диске».

## Ошибки из-за версий библиотек

Сервис ставит зависимости строго по файлу `requirements.txt`, где у каждой библиотеки заданы
проверенные границы версий. Если установка или запуск ломаются после обновления системы,
почти всегда причина в том, что в окружение попали версии вне этих границ.

**Проверить, что стоит в окружении:**

```bash
/opt/mailarchiver/venv/bin/pip list | grep -Ei 'fastapi|starlette|uvicorn|jinja2|pyyaml|apscheduler|imapclient|cryptography'
```

**Восстановить проверенный набор:**

```bash
sudo /opt/mailarchiver/venv/bin/pip install -r /opt/mailarchiver/app/requirements.txt
sudo /opt/mailarchiver/venv/bin/pip install --no-deps /opt/mailarchiver/app
sudo systemctl restart mailarchiver
```

Ключевой момент — флаг `--no-deps` при установке самого пакета. Без него pip заново подбирает
версии библиотек и может поставить непроверенные. Скрипты `install.sh` и `update.sh` начиная
с версии 1.1.0 делают это правильно; если вы ставили сервис вручную, используйте команды выше.

**Известные несовместимости:**

| Библиотека | Проблема |
|-----------|----------|
| `starlette` ≥ 0.29 | Изменилась сигнатура `TemplateResponse` (первым аргументом идёт `request`). Проявлялось как `TypeError: unhashable type: 'dict'` и пустая страница при открытии `/`. Исправлено в 1.1.0 — код работает с обеими сигнатурами. |
| `PyYAML` 6.0.2 и старше | Нет готовых пакетов под Python 3.14, установка уходит в сборку из исходников и падает. Нужна версия 6.0.3 и новее. |
| `APScheduler` 4.x | Полностью изменённый API планировщика, сервис с ним не работает. Граница `<4` в `requirements.txt` снята быть не может. |
| `IMAPClient` 4.x | Мажорная версия не тестировалась, ограничена `<4`. |

**Поддерживаемые версии Python:** 3.10–3.14. На более новых установка может не найти готовых
пакетов для части зависимостей — используйте Python 3.12–3.14.

sudo -u mailarchiver /opt/mailarchiver/venv/bin/mailarchiver \

## Проверка целостности локальной копии

В интерфейсе: меню ящика (⋯) → «Проверить целостность копии». Задание сверит файлы на диске с
индексом БД и сообщит об отсутствующих или повреждённых письмах.

## Рассинхронизация индекса и файлов

Если файлы копий были удалены/перемещены вручную, запустите проверку целостности, а затем повторный
бэкап — недостающие письма будут докачаны заново.

## «Слишком много неудачных попыток» у всех сотрудников сразу

Симптом: никто не может войти, все получают сообщение о блокировке, хотя пароль никто не подбирал.

Причина: сервис стоит за nginx/traefik, но `server.behind_proxy` выключен. Тогда адресом клиента
для всех запросов оказывается адрес самого прокси — и неудачные попытки одного человека (или бота,
который стучится снаружи) складываются в общий счётчик.

Решение — включить доверие прокси и обязательно перечислить его адреса:

```yaml
server:
  behind_proxy: true
  trusted_proxies: "127.0.0.1"    # адрес nginx; допустимы сети: 10.0.0.0/8
```

Обратная ситуация — блокировка не срабатывает вообще, хотя в логе видны сотни неудачных попыток.
Проверьте, что `trusted_proxies` содержит **только** адреса ваших прокси и не содержит `*`: со
значением `*` заголовку `X-Forwarded-For` верят от кого угодно, а его подделывает сам клиент.

Снять текущую блокировку можно, очистив счётчик:

```bash
sudo -u mailarchiver sqlite3 /var/lib/mailarchiver/mailarchiver.db \
  "DELETE FROM login_attempts WHERE success=0;"
```

## Вход «успешен», но каждая страница просит войти заново

Симптом: `/api/login` отвечает успехом, интерфейс мигает и возвращается на форму входа.

Причина: в разделе «Настройки» сохранено некорректное значение срока жизни сессии
(`security.session_ttl_hours`) или времени бездействия (`security.session_idle_minutes`) — cookie
выдаётся уже истёкшей. Начиная с версии 1.2.2 такие значения отклоняются при сохранении, но база,
испорченная более старой версией, продолжает их использовать.

Починить:

```bash
sudo -u mailarchiver sqlite3 /var/lib/mailarchiver/mailarchiver.db \
  "DELETE FROM settings WHERE key IN ('security.session_ttl_hours','security.session_idle_minutes');"
sudo systemctl restart mailarchiver
```

После перезапуска действуют значения из `config.yaml`.

## Все ящики помечены «пароль не читается»

Симптом: в списке ящиков у каждого стоит красная отметка «пароль не читается», копирование не
запускается и предлагает ввести пароль заново.

Причина: файл `/var/lib/mailarchiver/secret.key` заменён или утрачен — например, база восстановлена
из резервной копии, а ключ нет. Этим ключом зашифрованы пароли ящиков; без него расшифровать их
невозможно, и это не чинится ничем, кроме повторного ввода паролей.

Что делать:

1. Если старый `secret.key` ещё где-то есть (в бэкапе, на прежнем сервере) — верните его файлом,
   права `0600`, владелец `mailarchiver`, и перезапустите службу. Всё заработает.
2. Если ключ утрачен безвозвратно — откройте каждый ящик и введите пароль заново. Сами письма,
   индекс и настройки при этом целы: шифруются только пароли.

Начиная с версии 1.2.2 такая ситуация не ломает интерфейс — до версии 1.2.1 весь UI отвечал ошибкой
`Не удалось расшифровать сохранённый секрет ящика`, и добраться до страницы ящиков было нельзя.

## «Запрос пришёл с чужого сайта и отклонён»

Симптом: интерфейс открывается, но любое действие (сохранить, запустить копию) возвращает ошибку
`bad_origin`.

Причина: браузер сообщает один адрес сервиса, а сервер видит другой — обычно прокси не передаёт
заголовок `Host`. Решение: добавьте в конфигурацию внешний адрес, по которому пользователи
открывают интерфейс:

```yaml
server:
  public_url: "https://mail-backup.example.ru"
```

либо настройте прокси передавать `Host` (`proxy_set_header Host $host;`) или `X-Forwarded-Host`.

## Копия вне сервера: ошибки

| Сообщение | Что делать |
|-----------|-----------|
| «Папка для копии не найдена» | Сетевая папка или диск не подключены (не смонтированы) или путь с опечаткой. Проверьте `mount`, строку в `/etc/fstab`. Папки в `/home` и `/root` службе не видны (защита systemd `ProtectHome`) — подключайте в `/mnt` или `/srv`. |
| «Нет прав на запись в папку» | Служба работает от имени `mailarchiver`. Для локальной папки: `sudo chown -R mailarchiver: ПУТЬ`; для общей папки Windows — параметры подключения `uid=mailarchiver,gid=mailarchiver`. |
| «В месте для копии уже есть файлы» при подготовке | Папка не пустая и в ней нет метки этого архива. Выберите пустую папку или подтвердите использование этой (файлы вне `mailboxes/` и `db/` не трогаются). |
| «Метка копии … пропала, хотя копия здесь уже была» | Сетевая папка или диск не подключены (пустая точка монтирования), либо копию удалили. Подключите место копии. Если оно новое или очищено намеренно — «Подготовить место». |
| «В … лежит копия ДРУГОГО архива» | В месте копии — копия другого сервера MailArchiver (или база восстановлена из снимка). Если это ваша прежняя копия — «Подготовить место»: она будет принята и сверена. |
| «Ключ сервера-получателя изменился — возможна подмена сервера» | Если сервер-получатель переустанавливали — удалите его строку из `replica_known_hosts` в каталоге данных. Если нет — выясните, кто отвечает вместо него. |
| «Сервер-получатель не принял SSH-ключ службы» | Добавьте открытый ключ («SSH-ключ службы» или `sudo mailarchiver replica-ssh-key`) в `~/.ssh/authorized_keys` пользователя на сервере-получателе. |
| «На сервере-получателе не запускается rsync» | Установите rsync на сервере-получателе: `sudo apt install rsync`. |
| «Хранилище S3 отвергло запрос: часы сервера расходятся с точным временем» | Включите синхронизацию времени: `sudo timedatectl set-ntp true` (или chrony). |
| «Хранилище S3 отказало в доступе» | Неверный ключ доступа или у сервисного аккаунта нет прав на бакет (нужны чтение, запись и удаление объектов). |
| «Бакет … не найден» / «Хранилище S3 не принимает запрос» | Проверьте имя бакета, адрес и регион хранилища; для хранилищ, требующих адресацию бакета в имени сервера, выключите «Бакет в пути адреса». |
| «Удаление в копии приостановлено» | Прогон собирался удалить в копии слишком много файлов (больше «Защиты от массового удаления»). Так выглядит отключившийся диск с архивом. Если удаление ожидаемо (удалили ящики, большая очистка) — «Разрешить удаление и запустить». |
| Красная плашка «Копия вне сервера не обновлялась больше двух суток» | Откройте «Настройки → Копия вне сервера»: там итог последнего прогона и причина ошибки. |

## Письмо не показывается: «слишком большое для показа в браузере»

Это не ошибка. Письма крупнее 25 МБ не разбираются целиком: полный разбор занимает около
десятикратного объёма файла, и несколько таких открытий подряд роняли службу вместе с идущими
бэкапами. Заголовки такого письма видны, а содержимое и вложения можно получить кнопкой
«⬇ Скачать .eml» — вложения находятся внутри этого файла.

## Групповые действия и копирование по очереди

| Что видно | Что делать |
|-----------|-----------|
| Кнопка «Выполнить для N ящиков» не нажимается | Для необратимых действий (копия с нуля, удаление прежних копий, удаление ящиков) и восстановления в исходные папки без пробного прогона введите в поле подтверждения **число ящиков** — оно написано прямо в подсказке. Если в проверке 0 ящиков «будет обработано», смотрите «Почему пропущены». |
| «Пропущено: по ящику выполняется задание» | По ящику идёт копирование, экспорт или восстановление. Дождитесь окончания или отмените задание («Групповые действия → ⏹️ Отменить задания») и повторите. Если ящик сейчас копирует проход «все ящики по очереди», подождите, пока проход перейдёт к следующему ящику (или отмените сам проход в «Очереди и заданиях»). |
| «архив удерживается … — не пересоздаём / не удаляем» | На ящике удержание архива (увольнение, проверка). Копия «с нуля», удаление ящика (с архивом и без) и его прежних копий при удержании запрещены. Снимите удержание, если оно больше не нужно. |
| «Места на диске может не хватить» при копии «с нуля» | Прежние копии уходят в карантин и продолжают занимать место, а письма скачиваются заново — нужно примерно столько же свободного места, сколько занимают копии. Удалите старый карантин («🧺 Удалить прежние копии»), освободите диск или пересоздавайте ящики частями. |
| Проход «все ящики по очереди» не успевает за ночь | В итоге задания — «Время прохода вышло … не дошла очередь до N ящиков»: эти ящики будут первыми в следующий раз. Уменьшите паузу между ящиками, начните раньше или сдвиньте «не начинать новые ящики после». Первое копирование сотен ящиков сделайте параллельно («💾 Копия всех сейчас» → «Параллельно»). |
| «Сервер … не отвечает: 5 ящиков подряд без связи» | Почтовый сервер недоступен (сеть, DNS, перегрузка). Остальные его ящики в этом проходе пропущены и будут первыми в следующий раз. Если не скопирован ни один ящик, задание повторится само. |
| Проход по расписанию не запустился, в логе «копирование всех ящиков по очереди ещё идёт» | Прежний проход ещё не закончился — второй не ставится, прежний продолжает работу. |
| Ящики копируются дважды за ночь | У ящиков остались свои расписания копирования рядом с проходом по очереди. «Расписания» → «Удалить свои расписания ящиков…». |
| «Прежнюю копию не удаляем: прежняя копия не сравнивалась с новой» / «…писем, которых нет в новой» | Удаление прежних копий (из меню ящика и групповым действием) по умолчанию разрешено, только когда сравнение подтвердило, что все письма есть в новой копии. Нажмите «🔍 Сравнить», затем «🛟 Вернуть» (письма «только здесь» вернутся в архив) — после этого удаление пройдёт. Если письма точно не нужны — «Удалить» → «Удалить с потерей писем» (в групповом действии — снять флажок «Только прежние копии, все письма которых есть в новой копии»). |
| «Письма … не возвращаются: после копии «с нуля» копирование ещё не прочитало все папки ящика» | Новая копия ещё неполная: письма непрочитанных папок выглядели бы «только в прежней копии» и попали бы в архив дважды. Дождитесь копирования, которое прочитает все папки (ошибки отдельных писем не мешают), или разберитесь с папками — «🩺 Проверить папки на сервере»; папку, которую не починить, добавьте в «Пропускать папки» — тогда её письма можно вернуть. |
| В прежней копии «только здесь» есть письма из папок, которые сейчас не открываются | Такие письма не возвращаются — когда папка снова начнёт копироваться, они скачаются с сервера. Если папку на сервере не починить, добавьте её в «Пропускать папки» и сравните ещё раз. |
| «Писем старше срока хранения ящика не скачано: N» | Так и задумано: у ящика срок хранения, и ночная очистка всё равно удалила бы эти письма. Нужна вся история — увеличьте срок («Хранение копий» в меню ящика) или поставьте удержание архива: письма скачаются при следующем копировании. |
| «Сервер сменил нумерацию писем (UIDVALIDITY): узнано в архиве писем — N» | Почта переехала или папку пересоздали. Узнанные письма не скачивались повторно — делать ничего не нужно. |
| Поиск не находит письма одного ящика | Групповое действие «🔎 Переиндексировать поиск» для этого ящика: письма перечитываются, остальной индекс не трогается. |

## Сервер Axigen: ошибки

Подробно о разделе — [19-axigen.md](19-axigen.md). Каждая команда, отправленная серверу (и каждая
неудачная попытка), видна во вкладке «Журнал» раздела «Сервер Axigen» — пароль там скрыт.

| Сообщение | Что делать |
|-----------|-----------|
| «…соединение с … без шифрования — пароль администратора Axigen по сети так не отправляется» | Сервер архива и Axigen на разных машинах, а шифрование выключено. Добавьте в Axigen SSL-слушатель (WebAdmin → Services → CLI / FTP Backup & Restore → Listeners) и выберите шифрование в «Настройки → Сервер Axigen». «Разрешить без шифрования» — только для доверенной сети: пароль администратора будет виден в ней. |
| «нет соединения с …:7000» / «…FTP Backup…: нет соединения» | Слушатели CLI и FTP Backup у Axigen по умолчанию на `127.0.0.1` — с другой машины к ним не подключиться. Добавьте слушатель на сетевом адресе сервера и разрешите в его правилах доступа адрес сервера архива; проверьте межсетевой экран. |
| «сертификат сервера не прошёл проверку» | У сервера самоподписанный сертификат. «Проверить подключение» покажет отпечаток SHA-256 — сверьте его с сервером (`openssl x509 -noout -fingerprint -sha256 -in …`) и нажмите «Доверять этому сертификату». |
| «сертификат сервера не тот, которому разрешено доверять» | Отпечаток изменился. Если сертификат на сервере меняли — сверьте новый и доверьтесь ему заново. Если нет — соединение могли перехватить: выясните, кто отвечает вместо сервера. |
| «CLI Axigen не принял имя администратора» / «Неверный логин или пароль» | Проверьте логин и пароль администратора. Подойдёт и отдельный администратор Axigen с нужными правами. |
| «не прислал приглашение CLI Axigen» / «неожиданное приглашение» | На порту слушает не CLI (например, SSL-слушатель при выключенном шифровании или наоборот) — проверьте порт и «CLI через SSL». |
| «…не найден каталог домена…» / «…нет каталога ящика…» | В FTP Backup каталоги называются не так, как ожидалось. Сообщение показывает, что лежит в каталоге; укажите «Путь к ящику на FTP», например `domains/{domain}/{local}`. |
| «Изменения на сервере Axigen не разрешены» | Так задумано: по умолчанию MailArchiver только читает. Включите «Разрешить изменения на сервере», если действительно нужно менять сервер из MailArchiver. |
| «Сверки с сервером Axigen ещё не было» | Групповые действия Axigen работают по данным сверки. Раздел «Сервер Axigen» → «Сверить сейчас». |
| «…сервер не показал службы учётной записи — блокировать вслепую не будем» | Ответ сервера не удалось разобрать — блокировка не выполнялась. Откройте «Диагностику» этой учётной записи и журнал команд; закройте вход в WebAdmin. |
| «сервер не применил список служб» / «удаление не применилось» | Команда прошла, но проверка после неё показала, что сервер ничего не поменял (например, у администратора нет прав). Смотрите ответ сервера в журнале команд. |
| Восстановление через FTP: «писем на сервере не прибавилось» | Служба FTP Backup приняла файлы, но в папке их не видно. Проверьте права администратора на восстановление и журнал Axigen; письма в архиве не тронуты. |
| Плашка «Сервер Axigen: …» на дашборде | Проверка состояния нашла проблему: сервер недоступен, большая очередь, лицензия скоро кончается, ящики у предела квоты. Подробности — во вкладке «Обзор» раздела. |
| «Меняется защита соединения с Axigen (…) — введите пароль … заново в том же сохранении» | Вы меняете порт, выключаете шифрование или проверку сертификата, разрешаете «без шифрования» или меняете отпечаток. Сохранённый пароль по такому соединению без подтверждения не уходит — введите его в том же сохранении. Включить шифрование или проверку можно без пароля. |
| «Axigen не подтвердил команду … (нет ответа «+OK»)» | Сервер не прислал итог команды, которая меняет учётную запись, — изменение могло не примениться. Проверьте учётную запись в WebAdmin и ответ сервера в «Журнале команд»; повторите действие. |
| «по списку служб (…) не понять, открыт ли вход» | У учётной записи незнакомые службы или пустой список (службы могут наследоваться от домена). Задайте службы учётной записи явно в WebAdmin или закройте вход там. |
| «не все письма ящика есть в архиве — учётная запись НЕ удалена» | Перед удалением все папки сверяются с архивом. В сообщении — какие папки и сколько писем: включите копирование этих папок (или поднимите лимит размера письма) и повторите; если эти письма не нужны — отметка «Удалить, даже если часть писем не в архиве». |
| «Восстановление через FTP Backup Axigen … по расписанию оно не выполняется» | Восстановление через FTP Backup запускается только кнопкой администратора. Для расписания выберите «Как заливать: по IMAP» (у ящика должен быть пароль). |
| «Проверить ящик, который копируется через FTP Backup Axigen, может только администратор» | Проверка входит администратором Axigen, поэтому оператору и сотруднику недоступна. |

## Ящики на сервере: ошибки

Подробно о разделе — [20-server-bulk.md](20-server-bulk.md). Итог по каждому ящику — в «История» →
«Подробнее»; команды Axigen — в «Журнале команд» раздела «Сервер Axigen».

| Сообщение | Что делать |
|-----------|-----------|
| Плитка действия серая: «Недоступно: изменения на сервере Axigen не разрешены» | Действия, которые меняют учётные записи Axigen, работают только при «Разрешить изменения на сервере» («Настройки → Сервер Axigen»). Действия по IMAP, «Перечитать» и «Отчёт» доступны и без него. |
| «ящика нет в архиве — войти по IMAP нечем (пароля нет)» | Для действий по IMAP нужен ящик архива с паролем (или вход администратора почты, или OAuth2). Заведите ящик («Завести ящики в архиве» → «по IMAP с паролем») и впишите пароль. |
| «ящик копируется через FTP Backup Axigen — письма в архиве не связаны с номерами IMAP…» | Удалять письма по IMAP у такого ящика нельзя: архив не может сверить письма с сервером по номерам IMAP. Для учётных записей Axigen есть «Удалить старые письма (Axigen)» — в нём можно указать папку, например `Trash`. |
| «архив ящика хранит только последние N дн.» / «архив удерживается только до …» | Удалять старые письма и папки с письмами можно, только если архив хранит всё. Задайте ящику срок «хранить всё» или бессрочное удержание («Почтовые ящики» → меню ящика). |
| ««Папка»: N из M писем нет в архиве … — папка не тронута» | Письма пришли после копии, больше лимита размера, или папка исключена из копирования. Включите копирование папки (или поднимите лимит) и повторите — действие само сделает свежую копию. |
| «в папке есть другие письма с отметкой «удалено» …, а сервер не умеет стирать выборочно (нет UIDPLUS)» | Сервер без UIDPLUS стёр бы и чужие помеченные письма. Удалите или снимите отметку у этих писем в почтовой программе (или очистите папку там) и повторите. |
| «служб учётной записи не видно (наследуются от домена)» | Задайте службы учётной записи явно в WebAdmin — тогда их можно включать и отключать из MailArchiver. |
| «домен не разрешает: …» | Службы, которых нет в списке домена (WebAdmin → домен → Admin Limits → Available services), учётной записи не включить. |
| «занято … — больше новой квоты» | Такая квота остановила бы приём писем. Выберите квоту больше или сначала освободите место. |
| «Паролей для выдачи нет: файл уже скачан, прошло больше суток …» | Пароли для раздачи выдаются один раз и хранятся сутки. Если файл потерян — смените пароли этим учётным записям ещё раз. |
| «Для подтверждения введите число ящиков …» | Удаляющие действия подтверждаются числом обрабатываемых ящиков из окна проверки. |
| «Задание меняло почтовый сервер — кнопкой «Повторить» оно не запускается …» | Так задумано: повтор вслепую изменил бы ещё раз и уже изменённые ящики. Запустите действие заново из раздела «Ящики на сервере» (или «Сервер Axigen») — проверка покажет, что осталось сделать. |
| ««Папка» — не похожа на эту особую папку …» (очистка корзины или спама) | Указанная папка — не корзина (не спам): у неё нет отметки сервера и привычного имени в корне ящика. Другие папки очищает «Удалить старые письма (IMAP)» — только если архив хранит всё. |
| «в папке появились новые письма (…) — папка не удалена» | Пока шло удаление, в папку пришли письма, которых нет в архиве. Проверенные письма удалены, папка осталась; удалите её позже ещё раз. |
